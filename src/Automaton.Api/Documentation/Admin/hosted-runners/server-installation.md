# Server installation and setup

A server release installs the API, Studio, the public app store, Worker, PostgreSQL, RabbitMQ and Traefik. The installer supports Ubuntu and Debian 12 on x86_64 with public DNS. It installs a missing Docker Compose plugin automatically. It requires a published server release; it does not change an existing blue/green production installation.

After the installer finishes, open the one-time setup link printed by the installer and select **Check installation**. The link fills the token field and Studio removes it from the address bar. Studio never displays the saved token. Resolve any failing service checks, then create the first system administrator. Email delivery is optional at this stage. The setup token stops working when administrator creation commits. Sign in afterward.

System administrators can open **Admin → Installation** and select **Check installation** to inspect database/broker connections and configuration presence. **Verified** means a connection check succeeded; **configured** means a setting is present; **unverified** requires a manual or external check. Public DNS and inbound ports cannot be confirmed from inside the server. The page returns no saved secret values.

From a CLI session authenticated as a system administrator, run `automaton installation-status --json` to read the running release version, total users, apps and Runners, and the last successful nightly backup time. The equivalent API call is `GET /api/install/summary`. A Developer API key uses the role of its owning account. Use `automaton apps --json` to list apps in the signed-in account’s personal workspace.

The public app store at `store.<domain>` lists apps whose owners chose to list them; it is **Public** by default. Studio has no page for this setting; it is changed through the admin API (`PUT /api/admin/settings/store` with `mode` set to `public` or `disabled`). The store then shows that it is turned off, and its public catalog and creator endpoints return 404. Listings are kept and reappear when you set it back to **Public**. Running apps stay reachable at their own addresses either way.

Under **Outgoing email**, enter the SMTP host, port, TLS setting, account, password, sender and support addresses, then select **Save SMTP settings**. For an existing server-file configuration, enter its password to move to Studio-managed settings. After that, leave the password blank to retain it during edits. Select **Check connection** to verify TLS and account authentication without sending a message. Saving any change clears the previous verification. Enter a test recipient and select **Send test email** only when you want to send a real message. SMTP acceptance does not prove inbox delivery. The saved password is encrypted in the database and never displayed. The server-file configuration remains the fallback until Studio settings are saved; a decryption error blocks sending instead of falling back. Back up the database and API Data Protection key ring together so restored SMTP settings remain readable. A mounted key directory is not proof of an off-host backup.

The control plane needs a separate Machine Management Runner to execute applications. After CLI login, run `automaton runners install --name main --local` on the host, or use `--ssh user@host` from another machine. The CLI asks you to confirm the Runner's Docker host access; `--yes` confirms it for automation. It sends the one-time secret to sudo or SSH over standard input, waits for a connected Runner, and can add it to a project with `--project NAME`. Use [the Studio installation flow](./deployment-targets.md) if you prefer to enroll through Studio. The server installer does not grant Runner trust automatically.

On a fresh server, the first connected Runner also starts installation of **Server Console**, **Website Monitor** and **Heartbeat** from the official catalog into the first administrator's **Apps** list. The apps may take a minute to appear. They use the catalog's pinned commits, remain unpublished, and receive no permission approval. Configure and deploy each app when ready; review its requested permissions under **Admin → Apps**. To opt out before the Runner connects, set `Catalog.InstallEssentialsOnFirstRunner` to `false` in the server's `appsettings.Production.json` and restart the API. Delete any unwanted app through its **Settings → Danger Zone**. Existing servers do not install these apps automatically.

System administrators review app capability requests in **Admin → Apps**: it lists every app on the server with its owner, the menu entry shows how many requests are waiting, and **Waiting for approval** filters to them; **Review** opens the app's **Permissions** tab. App owners see the same request under the app's **Settings → Permissions**, and `automaton permissions status`, `automaton validate` and `automaton deploy` print a direct approval link for the administrator. A permission appears after the app requests it in `application.permissions` in `automaton.json` and deploys. Select **Approve** to issue the app a scoped credential, **Reject** to decline a pending request, or **Revoke** to invalidate an approved credential immediately. Two capabilities exist: `backups:read` and `server:read` (see **Server health for apps** below). The credential is delivered to the app as `APP_AUTOMATON_API_KEY` at the next Action run or runtime start. Approving or revoking also restarts the app's running copies on their Runners, so the change reaches a running app within moments, without a deploy; each new copy starts from the same deployed files and replaces the old one once it is ready. Revoking invalidates the old credential at once, even before the restart. Compose apps do not receive the credential and are not restarted. A copy being deployed at that moment restarts after the deployment; a copy whose Runner is offline gets the change at its next deploy or start. The app can use it as a bearer token for `GET /api/install/backups`. Removing the request and deploying invalidates the existing credential. App credentials cannot use other API endpoints, and they stop working while the app is hidden or disabled. Approval applies to the app, not to one build, so approve only apps whose owner you trust with that capability. `APP_AUTOMATON_API_KEY` is reserved and cannot be used as an app secret name. Approvals, rejections and revocations, and every secret change and delivery (names, scopes and versions, never values), appear under **Admin → Audit Events**; secret entries are kept for 180 days.

System administrators can update the server without SSH. In **Admin → Installation → Update**, select **Update to the latest release** and confirm; the card shows the current version, live status, the log and the recovery backup name, and keeps reconnecting while the API restarts. From the CLI, `automaton server update --wait` does the same and then checks `/health` and `automaton installation-status`; `automaton server update-status` shows the last run (add `--version server-vX.Y.Z` to choose a release). The API never runs as root: it only writes a request that a root systemd unit on the server validates and hands to the updater below, so its checks and recovery backup apply. The API is `GET` and `POST /api/install/update` (system administrators; Developer API keys use their owner's role). A server installed before this feature reports that updates from Studio are not enabled until `update.sh` has been run once over SSH.

To update a standalone server over SSH, run `sudo bash /opt/automaton-server/update.sh --version server-vX.Y.Z` on the host using a published release. The updater verifies the bundle, saves a protected recovery backup of the database, configuration and Data Protection keys, and checks health after updating compatible API, Worker and Studio images. Keep that backup in encrypted off-host storage. Releases that change Compose or infrastructure image digests need a separately reviewed migration. The installer itself only resumes its original release. See [server installation and updates](../../../../../docs/prod/install-automaton.md) for recovery and offline bundle instructions.

## Server health for apps

An app that requests `server:read` and is approved (see above) can call `GET /api/server/health` with its `APP_AUTOMATON_API_KEY`. The answer is read-only: server and Runner versions and whether a newer release exists, OS name and version, uptime, CPU, load, memory and disk, Docker disk use, pending and security updates, whether a restart is required (and since when), certificate expiry of the Studio and API host names, and the last backup. Apps without the approval, and API keys, get 403. The Machine Management Runner measures the host figures every 5 minutes and reports them, so they are missing until the Runner has reported once and can be up to a few minutes old. To read them it starts a short-lived container with no network and read-only access to the host files `/etc/os-release`, `/run/reboot-required` (when present) and, on Ubuntu, `/var/lib/update-notifier`. Update counts come from Ubuntu's update notifier and are empty on hosts without it. Upgrade the Machine Management Runner (**Upgrade available** in Studio) so it reports.

## Backups

**Backups** (system administrators) lists the server's nightly backups with their time, size and the command that restores each one. Each backup also has an encrypted archive, readable by approved apps with `backups:read` at `GET /api/install/backups/{name}/archive`; the API accepts only names in the backup list and streams from a read-only host mount. Studio shows the public age recipient and the sudo command for reading the private backup key; save that key in a password manager because an archive cannot be restored without it. `restore.sh --archive FILE --key FILE` decrypts and restores an archive. It does not contain all `/etc/automaton` secrets; copy those separately to recover existing signing credentials and sessions. The **Backups** check under **Configuration status** is *configured* when the last backup succeeded within 36 hours, *error* when it failed or is older, and *unverified* on servers that have not received backups yet (run the latest server update). Studio cannot start a backup or a restore: both run on the server with sudo, because restoring stops the API that serves Studio.

- **Back up now:** `sudo bash /opt/automaton-server/backup.sh`
- **Restore:** copy the backup's command from Studio and run it on the server. It asks for the server domain, saves the current state as a new backup, then replaces the whole database and Data Protection keys. Everything written after the backup is lost.

Nightly backups stay on the server. Turn on the hosting provider's server backups and keep an off-server copy as described in [backups and restore](../../../../../docs/prod/install-automaton.md#backups-and-restore).

Other server configuration belongs to the host operator. Optional OAuth and billing settings are edited in the protected host configuration and applied by recreating API/Worker. Protect the configuration, database, application data and persistent cryptographic keys with encrypted off-host backups. Losing encryption keys can prevent recovery even when the database survives.
