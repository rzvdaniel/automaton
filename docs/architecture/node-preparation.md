# Node preparation boundary

`src/Automaton.Node` remains an opt-in, non-enrolled .NET generic-host service. It is not installed or used by existing Runner/API/Worker paths. Its empty application configuration has no environment, command-line, JSON or secrets providers; `Program` reads only the explicit non-secret `AUTOMATON_NODE_HOST_STATE_DIRECTORY` variable. Startup requires Linux x64, effective UID 0, an existing canonical root-owned directory with no group/world write, and an allow-listed local filesystem. The service opens a fixed `node-manager.lock` with no-follow semantics, validates its owner/mode/type/link count, and holds an exclusive nonblocking kernel `flock` for the manager lifetime. It never removes or replaces the file. Once locked, its local phase is `RecoveryRequired`, capabilities remain unknown and workload admission remains disabled. The local identity, journal, external restore authority, API activation/recovery adapter, broker, Docker and executor are absent, so this state does not claim authenticated recovery or host fencing. Existing Runner behavior and registrations are unchanged.

The API now has a bounded, fail-closed N1-A activation persistence slice behind the reviewed Node management listener. `NodeManagement`, `NodeActivationAttempt` and `NodeHostFenceReceiptUse` persist realm/credential/epoch binding, incarnation allocation, immutable same-request receipts and single-use HFA receipt consumption. The initial activation accepts the explicit expected-incarnation sentinel `0` only while the current incarnation is null and allocates incarnation `1`; later activation uses a positive expected incarnation and a conditional update that includes the expected `RecoveryEpoch`. Every result remains `Recovering`. No API transition sets `Active`, and no Node process consumes these receipts yet.

Activation remains operationally disabled: the production HFA trust store must be configured and the independent recovery-epoch authority adapter is deliberately unavailable until its owning operational slice. Missing either dependency fails closed. This persistence/API code grants no broker, Docker, executor, workload or host authority. Its migration and isolated acceptance evidence are recorded in [N1-A activation persistence](../roadmap/node-execution/results/N1-A-activation-persistence.md); the reviewed contract remains [N1-A activation/recovery specification](../roadmap/node-execution/results/N1-A-activation-recovery-spec.md).

`Capabilities/NodeCapabilityValidator` is a pure validation function over caller-supplied **unverified** observations. It accepts bounded Linux/x64/Docker/cgroup-v2/XFS-shaped facts, rejects missing/unsupported/malformed/oversized facts, and produces enum diagnostics with a copied read-only snapshot on success. Text fields are limited to 128 characters without control characters; storage collections to 64 entries. Volume IDs must be unique/nonempty; filesystem UUIDs must be nonempty canonical GUIDs and project IDs positive. Distinct volume aliases may share a quota domain. These are parsing/support-shape checks, not proof of kernel configuration, quota enforcement, freshness or ownership. `CanAdmitWorkloads` is always false and eligible workload kinds are always empty. Missing host facts remain unknown; startup performs no discovery.

The executable references generic hosting plus a narrowly allow-listed filesystem/native-lock surface. Architecture tests constrain its project graph to the reviewed future management boundary, its direct package to generic hosting, and its compiled type references against networking, child-process execution and tenant/legacy execution. Lifecycle tests inspect resolved hosted services and configuration providers; the Linux process fixture exercises contention, crash release, stable lock-file identity and the non-admitting restart state. These tests guard accidental dependencies; they are not a sandbox or an independent security review.

## Narrow future shared-RM extraction

No `Automaton.Execution.Management` project exists yet. Creating an empty library or moving operational code now would not serve a current consumer and would cross the preparation scope. The following boundary is the extraction contract for separately authorized, reviewed N1 work; it does not authorize implementing it.

| Existing source seam in `src/Automaton.Runner/Services/` | Future shared mechanics | Remains with owning feature / prerequisites |
| --- | --- | --- |
| `RunnerExecutionQueueConsumer` | Bounded delivery-channel lifetime, callback/ack ordering and cancellation mechanics | Exact queue authorization, Node enrollment/authentication and identity dispatch remain adapters. No Node broker consumer before reviewed N1-A/B. |
| `RunnerExecutionApiClient` / `InfrastructureResultDelivery` | Narrow HTTP lifetime/retry/receipt mechanics, where both hosts need identical semantics | Existing bearer setup, Runner identity headers, route decisions and artifact filesystem writes are not copied into Node defaults. Selected authentication and Node digest/receipt contracts must be implemented explicitly. |
| `RunnerExecutionJournal` | Journal storage/atomic-write mechanics only after reviewing the actual shared semantics | Current journal lacks Node realm/epoch fencing and required directory fsync. Node fence/identity/acceptance/retention policy remains Node-owned; no claim that a rename extracts a compliant journal. |
| `RunnerExecutionDeliveryHandler` / `RunnerExecutionProcessor` | Only independently identified common delivery primitives | Tenant executors, file transfers, tunnel reconnect handlers and legacy command interpretation stay outside Node management DI. Do not transplant these classes wholesale. |

The future library may depend on Core/Messaging and narrowly necessary .NET/RM packages, never Runner, Steps, Core.Scripting, API, Worker or Infrastructure. Core retains data-only wire contracts; the library must not own placement, quota, authentication selection, Node fence policy, tenant execution or a second transport/operation store. Runner and Node must be real consumers before extraction; existing Runner cancellation, retry, queue scope, journal/receipt and result behavior need regression coverage. No existing Runner file or project reference is changed by preparation.

The [N0-D contract and readiness](../roadmap/node-execution/results/N0-D-architecture-and-acceptance.md) owns future decisions. [Limited N1-A preparation evidence](../roadmap/node-execution/results/N1-A-node-enrollment.md), [activation persistence evidence](../roadmap/node-execution/results/N1-A-activation-persistence.md) and [local startup/installation-lock evidence](../roadmap/node-execution/results/N1-A-node-local-startup-lock.md) record the implemented slices. Local identity/epoch validation, authenticated recovery, API activation adapter, mTLS selection, independent review and deployed-path evidence remain pending. There is no supported Node install/production workflow; no current Admin workflow changes.
