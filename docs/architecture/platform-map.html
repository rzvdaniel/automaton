    Docker siblings; shared account ceiling

    The trusted host creates app/build containers with the Hosted Runner’s cgroup parent. They are not Docker-in-Docker children of the Hosted Runner. The account budget includes the agent’s own consumption.

    Logical identities outlive containers

    An app owns environments (deployment targets). Each target has its Runner assignment, runtime state and route. Replacement candidates can coexist briefly; a Docker ID is an execution artifact.

    App → Environment → Runner → Host

    Storage makes placement sticky

    Targets have separate deployed state, while persistent data is app-scoped in the managed account volume. A container can be replaced without moving that data. Reusing an XFS project ID on another filesystem does not move data or create a global quota.

    04 / Complexity

    Keep the boundaries. Reduce repeated machinery.

    A qualitative source review, not a measured complexity score. The costly parts are state transitions, retries and authority spread across services.

    Complexity that earns its place

    • API policy versus privileged execution

      The API reconstructs authorized app, target, host and resource scope; the Infrastructure Runner applies host changes.

    • Durable intent versus actual runtime

      Database operation state and Runner journals handle redelivery and interrupted callbacks. Uncertain execution must not be blindly repeated.

    • Tenant budgets versus host headroom

      Aggregate cgroups, account XFS quotas and shared Docker storage protect different resources.

    • Serving versus deployment

      Managed HTTP traffic flows through Traefik and the Hosted Runner gateway, independently of Worker and command queues. A running app container alone does not guarantee gateway availability. BYO adds the API/SignalR tunnel dependency.

    Complexity we can reduce

    • Several durable operation families

      Hosted deployment commands, general Runner executions and Infrastructure host-container work repeat dispatch, status, retries and result delivery.

    • Nested asynchronous orchestration

      A Hosted Runner requests host work through the API, which persists another operation and dispatches it to Infrastructure. Synchronous waits inside a message consumer can block the queue needed to complete that work.

    • Limits described in different units

      Plan allowance, specification, assigned target count, active workloads and host capacity can describe different things under similar labels.

    • Many recovery-specific paths

      Registration, restart, deployment, storage and host provisioning have distinct reconciliation responsibilities. Shared lifecycle rules could reduce drift without creating a single giant service.

    05 / Recommended direction

    Make fewer decisions in fewer places

    PROPOSALS · NOT IMPLEMENTED BY THIS PAGE
    Ordered by dependency and expected simplification. No runtime migration or production change is included.

    01

    Share a small durable-operation core

    Start with common result delivery, retry disposition and operation correlation across existing command families. Keep typed payloads, authorization, queue separation and domain-specific completion rules.

    First reviewable sliceInventory duplicated transitions and extract one proven common policy. Gate it with duplicate delivery, wrong-Runner rejection, lost callback and process-restart tests. Avoid a new generic workflow engine or database migration as the starting point.
    02

    Make orchestration resume from durable state

    Replace long awaited child work inside broker handlers with persist → dispatch → return → resume on completion, where current dependencies can block progress. Keep execution ownership and cancellation explicit.

    Why this comes nextThe recorded scheduled-dispatch deadlock demonstrates the risk. Dedicated consumer groups are a useful immediate safeguard; a resumable operation removes the dependency on an occupied consumer. Prove recovery with several Workers and API replicas.
    03

    Use one resource vocabulary and policy owner

    Keep the existing specification snapshot authoritative. Project it into admission, host enforcement and Studio reporting. Clearly name assigned-target allowance, running-app allowance and concurrent-work allowance before adding new semantics.

    Preserve the contractDo not silently reinterpret MaximumApps. Any running-app policy needs explicit migration and restart/recovery behavior. Verify concurrent admission, failed cleanup, pending resize and downgrade reservations.
    04

    Keep Hosted execution thin; centralize host mechanics

    Retain the Hosted Runner as the account-scoped execution agent. Keep all privileged Docker and cgroup operations behind Infrastructure. Consolidate repeated ownership checks and create/adopt verification at that boundary.

    Proof before removalVerify ownership and actual cgroup membership when adopting existing containers. Longer term, assess whether a host supervisor can replace the per-account agent—but only after accounting for Actions, files, workspaces, gateway serving, credentials and recovery.
    05

    Separate the static-site product path

    For truly static published artifacts, consider one safe shared serving path with explicit quotas and atomic publication. This can avoid reserving a dynamic runtime for each static site.

    A bounded feature, not a shortcutCurrent source does not establish general runtime-free static hosting. Require export allowlists, authentication behavior, atomic publish/rollback and capacity accounting. Never expose a source or private data directory as a web root.
    Proposed internal shape / existing product boundaries

    One policy authority. One durable operation pattern. Two execution privileges.

    Studio / CLI→API · policy + durable intent→RabbitMQ · addressed work→Hosted or Infrastructure Runner

    HTTPS carries assignments, artifacts and results. Worker schedules and reconciles. Traefik serves runtime routes. Keep stable app/target identities, account storage affinity and separate tenant/host credentials throughout.
