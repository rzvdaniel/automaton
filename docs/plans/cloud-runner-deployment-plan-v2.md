# Cloud Runner Deployment Plan

## Executive Summary

This document outlines the plan for implementing Cloud Runners - a feature that allows users to create managed Runner instances on shared Hetzner servers. The approach uses **Management Runners** (installed as services on each server) that execute flows to deploy/manage user Cloud Runner containers.

### Key Design Decisions

1. **No Hetzner API Integration** - Servers are created manually via Hetzner Console
2. **No ContainerAgent** - Use existing Runner infrastructure instead
3. **Flows as Infrastructure** - Docker operations via Python/Bash flows
4. **Management Runners** - One privileged Runner per server manages all containers
5. **Admin-Only Execution** - Only Admins can trigger infrastructure flows
6. **User Choice** - Users select server based on location/specs/price

## Database Schema

### CloudServer Entity

Represents a Hetzner server registered in the system.

```csharp
public class CloudServer
{
    public Guid Id { get; set; }
    
    // Display information
    public string Name { get; set; }                    // "EU-Nuremberg-1"
    public string Location { get; set; }                // "nbg1"
    public string LocationDisplayName { get; set; }     // "Nuremberg, Germany"
    public string CountryCode { get; set; }             // "DE" (for flag display)
    
    // Server specifications
    public string ServerType { get; set; }              // "cx41"
    public string Specs { get; set; }                   // "4 vCPU, 16GB RAM, 160GB SSD"
    public string IpAddress { get; set; }               // "95.216.xxx.xxx"
    
    // Capacity management
    public int MaxCapacity { get; set; }                // 25
    public int CurrentUsage { get; set; }               // 18
    
    // Management Runner reference
    public Guid? ManagementRunnerId { get; set; }       // FK to Runner
    public Runner ManagementRunner { get; set; }
    
    // Pricing (for display to users)
    public decimal PricePerRunner { get; set; }         // 0.70 (€/month)
    public string Currency { get; set; }                // "EUR"
    
    // Status
    public CloudServerStatus Status { get; set; }       // Active, Maintenance, Offline
    
    // Timestamps
    public DateTime CreatedAt { get; set; }
    public DateTime UpdatedAt { get; set; }
    
    // Navigation
    public ICollection<CloudRunner> CloudRunners { get; set; }
}

public enum CloudServerStatus
{
    Active,
    Maintenance,
    Offline
}
```

### CloudRunner Entity

Represents a user's Cloud Runner container on a server.

```csharp
public class CloudRunner
```

## Management Flows

These are pre-built flows that only Admins can execute. They run on the Management Runner of each server.

### Flow 1: Deploy Cloud Runner

**Input Variables**:
| Variable | Type | Description |
|----------|------|-------------|
| `userId` | string | User's GUID |
| `apiKey` | string | Generated API key for the runner |
| `runnerName` | string | Display name |
| `containerName` | string | Docker container name |
| `tier` | string | "free", "pro", or "enterprise" |
| `apiUrl` | string | Studio.Server URL |
| `imageTag` | string | Runner image tag (default: "latest") |

**Bash Script**:
```bash
#!/bin/bash
set -e

# Input variables (injected by flow engine)
USER_ID="{{userId}}"
API_KEY="{{apiKey}}"
RUNNER_NAME="{{runnerName}}"
CONTAINER_NAME="{{containerName}}"
TIER="{{tier}}"
API_URL="{{apiUrl}}"
IMAGE_TAG="{{imageTag}}"

# Registry (GitHub Container Registry)
IMAGE="ghcr.io/rzvdaniel/automaton-runner:${IMAGE_TAG}"

# Resource limits based on tier
case $TIER in
  "free")
    CPU_LIMIT="0.25"
    MEMORY_LIMIT="256m"
    ;;
  "pro")
    CPU_LIMIT="0.5"
    MEMORY_LIMIT="512m"
    ;;
  "enterprise")
    CPU_LIMIT="1.0"
    MEMORY_LIMIT="1g"
    ;;
  *)
    CPU_LIMIT="0.25"
    MEMORY_LIMIT="256m"
    ;;
esac

echo "Pulling image: ${IMAGE}"
docker pull "${IMAGE}"

echo "Creating container: ${CONTAINER_NAME}"
docker run -d \
  --name "${CONTAINER_NAME}" \
  --restart unless-stopped \
  --cpus="${CPU_LIMIT}" \
  --memory="${MEMORY_LIMIT}" \
  --memory-swap="${MEMORY_LIMIT}" \
  --pids-limit=100 \
  --security-opt=no-new-privileges:true \
  -e AUTOMATON_API_URL="${API_URL}" \
  -e AUTOMATON_API_KEY="${API_KEY}" \
  -e AUTOMATON_RUNNER_NAME="${RUNNER_NAME}" \
  -e AUTOMATON_USER_ID="${USER_ID}" \
  "${IMAGE}"

echo "Container ${CONTAINER_NAME} started successfully"

# Output container ID for reference
docker inspect --format='{{.Id}}' "${CONTAINER_NAME}"
```

### Flow 2: Remove Cloud Runner

**Input Variables**:
| Variable | Type | Description |
|----------|------|-------------|
| `containerName` | string | Docker container name |

**Bash Script**:
```bash
#!/bin/bash
set -e

CONTAINER_NAME="{{containerName}}"
```


### Flow 6: Install Docker (One-time Setup)

**Input Variables**: None

**Bash Script**:
```bash
#!/bin/bash
set -e

echo "Installing Docker..."

# Update package index
apt-get update

# Install prerequisites
apt-get install -y \
    apt-transport-https \
    ca-certificates \
    curl \
    gnupg \
    lsb-release

# Add Docker's official GPG key
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | gpg --dearmor -o /usr/share/keyrings/docker-archive-keyring.gpg

# Set up stable repository
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/docker-archive-keyring.gpg] https://download.docker.com/linux/ubuntu \
  $(lsb_release -cs) stable" | tee /etc/apt/sources.list.d/docker.list > /dev/null

# Install Docker Engine
apt-get update
apt-get install -y docker-ce docker-ce-cli containerd.io

# Start and enable Docker
systemctl start docker
systemctl enable docker

# Verify installation
docker --version
docker run hello-world

echo "Docker installed successfully!"
```

## Setup Procedure (Manual Steps)

### Setting Up a New Hetzner Server

1. **Create Server via Hetzner Console**
   - Choose server type (CX21/CX31/CX41/CX51)
   - Choose location (nbg1, fsn1, hel1, ash, etc.)
   - Choose Ubuntu 22.04 LTS
   - Add your SSH key

2. **SSH into Server**
   ```bash
   ssh root@<server-ip>
   ```

3. **Install Docker** (or run the Install Docker flow later)
   ```bash
   curl -fsSL https://get.docker.com -o get-docker.sh
   sh get-docker.sh
   ```

4. **Install Management Runner**
   ```bash
   # Download runner
   mkdir -p /opt/automaton-runner
   cd /opt/automaton-runner
   
   # Download latest release (or use install script)
   wget https://studio.automaton.monster/downloads/runner/latest/automaton-runner-linux-x64
   chmod +x automaton-runner-linux-x64
   
   # Create config
   cat > appsettings.json << EOF
   {
     "ApiUrl": "https://studio.automaton.monster",
     "ApiKey": "<ADMIN_GENERATED_API_KEY>"
   }
   EOF
   
   # Create systemd service
   cat > /etc/systemd/system/automaton-runner.service << EOF
   [Unit]
   Description=Automaton Management Runner
   After=network.target docker.service
   Requires=docker.service

   [Service]
   Type=simple
   User=root
   WorkingDirectory=/opt/automaton-runner
   ExecStart=/opt/automaton-runner/automaton-runner-linux-x64
   Restart=always
   RestartSec=10

   [Install]
   WantedBy=multi-user.target
   EOF
   
   # Enable and start
   systemctl daemon-reload
   systemctl enable automaton-runner
   systemctl start automaton-runner
   ```

5. **Register in Automaton Studio**
   - Go to Admin > Cloud Servers
   - Click "Register Server"
   - Fill in details and select the Management Runner

## Security Considerations

### Management Runner Security

- Runs as root with Docker socket access
- API key is admin-level, never exposed to users
- Only accessible by Admin users for flow execution
- Marked as `IsManagementRunner = true` in database

### Cloud Runner Isolation

- Each container has resource limits (CPU, memory, PIDs)
- Runs with `--security-opt=no-new-privileges:true`
- Cannot access Docker socket
- Cannot access other containers
- Unique API key per Cloud Runner

### API Security

- Cloud Runner endpoints require authentication
- Users can only manage their own Cloud Runners
- Server registration/management requires Admin role
- Management flow execution requires Admin role

## Appendix: Flow Templates Storage

Management flows should be stored as **system templates** that can be referenced by ID. Options:

1. **Database-stored flows** with `IsSystemFlow = true`
2. **Embedded resources** in the assembly
3. **Configuration files** deployed with the server

Recommendation: Use database-stored flows with a seeding mechanism on startup.
