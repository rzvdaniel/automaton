# Cloud Runner Architecture Discussion

## Date: December 18, 2024
## Branch: hetzner-runner-container

---

## Context

We are implementing a cloud runner auto-deployment feature that allows users to create "Cloud Runners" that are automatically provisioned on Hetzner Cloud servers.

### Current Setup

- **Automaton.Studio** (Blazor UI) - Runs on your own hosting
- **Automaton.Studio.Server** (API) - Runs on your own hosting  
- **Automaton.Runner** - Existing runner that connects to Studio.Server via SignalR

## Discussion: Do We Need ContainerAgent?

### Question 1: Why a Separate Automaton.ContainerAgent?

**Initial reasoning**: 
- Studio.Server runs on your hosting
- ContainerAgent runs on Hetzner servers
- ContainerAgent manages Docker containers on those servers

**Your clarification**:
- Automaton.Server and Automaton.Studio run on YOUR hosting (not Hetzner)
- You only want to deploy Runner containers on Hetzner for users

### Question 2: Can't We Just Use Hetzner API?

**Answer**: Yes! Hetzner has a full API. We explored options:

#### Option 1: One Hetzner Server Per User (Simple but Expensive)
```
User clicks "Create Cloud Runner"
    ? Studio.Server calls Hetzner API to create a CX11 server (~€3.29/mo)
    ? Server boots with cloud-init that runs Runner container
    ? Runner connects to Studio.Server via SignalR
```
- **Pros**: Simple, no ContainerAgent needed
- **Cons**: ~€3.29/user/month (dedicated server per user)

#### Option 2: Shared Servers with Multiple Containers (Cost-Effective) ?
```
Hetzner Server 1 (CX41 - €17.49/mo)
??? User A Runner container
??? User B Runner container
??? User C Runner container
??? ... (up to 25 containers)

Hetzner Server 2 (created when Server 1 is full)
??? User X Runner container
??? ...
```
- **Pros**: ~€0.70/user/month, better resource utilization
- **Cons**: Need something to manage containers on each server

---

## Question 3: Where Does the Runner Image Come From?

The runner Docker image needs to be published to a **container registry**:

| Registry | URL Format | Cost |
|----------|------------|------|
| **Docker Hub** | `automaton/runner:latest` | Free (public) |
| **GitHub Container Registry** | `ghcr.io/rzvdaniel/runner:latest` | Free |
| **Self-hosted** | `registry.automaton.monster/runner:latest` | Your cost |

**Recommendation**: Use GitHub Container Registry (ghcr.io) since code is already on GitHub.

### Options to Manage Containers on Remote Hetzner Servers:

| Approach | How It Works | Pros | Cons |
|----------|--------------|------|------|
| **ContainerAgent** | REST API on each server | Full control, custom logic | Extra service to deploy |
| **Docker Remote API** | Expose Docker API (TLS) | Standard, no extra service | Security concerns |
| **SSH + Docker** | SSH to run docker commands | Simple | Slower, harder to manage |

---

## Conclusion: Yes, ContainerAgent Makes Sense

For **shared servers with multiple containers**, you need something on each Hetzner server to manage Docker containers. The ContainerAgent we built does exactly this.
