# Release install check

Every published server release is installed on a throwaway Hetzner server and checked by script, so a broken install, Runner connect or upgrade shows before production.

- Workflow: `.github/workflows/release-install-check.yml` (starts after `Publish Automaton Server` succeeds; run it by hand with an optional version). Script: `scripts/ci/release-install-check.sh`.
- Secrets (owner creates both): `HCLOUD_TOKEN` for the separate Hetzner project `automaton-ci` only, and `CLOUDFLARE_DNS_TOKEN` with Zone.DNS edit on `automatontest.fyi` only.
- With the secrets `CI_TLS_CERT` and `CI_TLS_KEY` set, installs use `--tls-mode custom` on the fixed names under `ci.automatontest.fyi` (no Let's Encrypt request per run; the rebuilt server keeps the same names). Workflow `ci-certificate.yml` issues that wildcard (`*.ci` and `*.apps.ci`, DNS-01) monthly and stores it. It needs the owner to create the secret `CI_SECRETS_TOKEN` once (fine-grained token, Secrets and Variables read/write on this repository). A weekly check fails when fewer than 20 days remain. A release whose installer predates `--cert-file` (upgrade from an old version) and a run without the secrets fall back to the next line.
- Weekly default-path check: Sunday 22:17 UTC the workflow runs `fresh` with `tls: letsencrypt` (also a manual input): real Let's Encrypt certificates on a per-run sub-domain, about 5 a week. The summary shows the issuer Studio really serves.
- Fallback: each install uses its own sub-domain of `automatontest.fyi` (Let's Encrypt allows five certificates a week per set of names).
- Flow: create a server with the first-boot snippet from the install page (`--unattended --domain automatontest.fyi`), set the A records through Cloudflare (proxy off, TTL 60), wait for health, then check health, Studio and API (200), the admin link and password, CLI login, the `main` Runner connected, and a hello app that is created, deployed, published and answers 200. One server serves the whole run (`release-install-check.sh all`, the default; a manual run can pick `fresh`, `upgrade` or `restore` alone). It first installs the previous release, runs `automaton server update --version <new> --wait` repeats the checks and the external scan, takes the backup (see Restore), rebuilds the same server (`hcloud server rebuild --image ubuntu-24.04`, same IP, our SSH key re-added by cloud-init), installs the release fresh, checks and scans it, restores, and deletes the server.
- Server types are tried in order (`cx23`, then `cpx12`), across `nbg1`, `fsn1`, `hel1`: both are workflow inputs. The summary names the type and location that ran; a failure on `cpx12` that looks like memory is reported as such.
- Cleanup: the script deletes the server, SSH key and DNS records on exit, the workflow deletes leftovers of its run in an `if: always()` step. Check Hetzner for leftover `automaton-ci` servers after a cancelled run.
- A failing check fails this run, not the release run that already published.
- External scan: at the end of each mode, while the server still runs, `scripts/ci/release-scan.sh` runs the OWASP ZAP baseline (passive, unauthenticated) from the runner against Studio, the API health URL, the store and the published hello app, and nmap against all ports. `scripts/ci/scan-report.py` fails the run on high findings, missing security headers (CSP, clickjacking, HSTS, nosniff, server version leak) and open ports other than 22, 80 and 443; other medium findings are listed in the run summary. Accepted findings go in `scripts/ci/scan-allowlist.txt` with a reason each. Studio crawling and the authenticated Studio scan are the weekly full scan below.
- API scan: on the fresh install only, the workflow builds the release's `openapi.json` from the tag's source (`swagger tofile`; Swagger stays off on servers; a separate job without secrets builds it from a published release only), the script creates a developer CLI key on the throwaway server and `release-scan.sh --api-spec` runs `zap-api-scan.py` against every endpoint of the file with that key as the `Authorization` header (at most 15 minutes). Endpoints that update, restart, clean up or uninstall the server, or change users and sign-in, are listed in `scripts/ci/api-scan-exclude.txt` and removed from the file before the scan. The run summary shows how many endpoints were scanned. A stack trace in an answer (ZAP 90022) fails the run; highs and the other findings follow the same rules and `scan-allowlist.txt` as above.
- Restore: after the upgrade phase the script writes a marker file into the hello app's data directory in the Runner workspace volume and takes a backup. It copies the newest `.tar.age` and the backup key (kept in `secrets/backup-key` by the unattended install) through the runner's private work directory, rebuilds the server with a fresh install of the release, runs `restore.sh --archive --key --confirm <domain>` there, and checks that Studio answers, the first install's administrator password signs in, the app is listed and the marker file is back. The server is deleted on exit. Run by hand with `restore_wrong_key` ticked to prove the failure path: the restore stops at decryption and the run fails with "Restore failed". The external scan runs after the upgrade and after the fresh install.

- Production scan: the last job of `Deploy production` (`scan`) runs `release-scan.sh --zap-only` (passive ZAP baseline against Studio, `api/health`, store and the website; no nmap, no signed-in or active scan). A finding does not roll the deploy back: it fails the job, lists the findings in the run summary and opens one issue for the owner to put in the board 17 Inbox.

- Weekly full scan: `.github/workflows/security-full-scan.yml` (Sunday 21:43 UTC, or run by hand; shares the concurrency group with this check) installs the newest server release on a throwaway server (`release-install-check.sh fullscan`) and runs `scripts/ci/release-full-scan.sh` with the ZAP automation plan `scripts/ci/zap-full-plan.yaml`: the AJAX spider crawls Studio signed in as the install's administrator (browser login on `/login`), the API comes from the release's OpenAPI file with a CLI key, and ZAP's active scan attacks both. Active scans create junk data, so it never runs on the shared test server or production. Endpoints in `api-scan-exclude.txt` and the logout page are excluded. The summary shows the Studio routes found and how many sit behind the sign-in; the run fails when none do. Verdict as in the external scan (`scan-allowlist.txt` is shared): highs, missing security headers and stack traces fail the run and each new one opens an issue for the owner to put in the board 17 Inbox (a finding that already has an issue is not filed again); mediums are listed in the summary. It never blocks a release. Timeout 150 minutes, one server per run, deleted on exit and by the workflow's cleanup step.
