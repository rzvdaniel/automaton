### Restore fencing: an epoch outside the restored database

N0-C requires monotonic fencing to survive restore but did not identify its authority. **Selected proposed protocol: supervised offline restore with an independently retained recovery fence register.** No online/in-place database rewind is supported. Host-local maxima alone cannot detect a restored database from an unreachable host, and a high generation in a restored row cannot prove it is the latest. Time, heartbeat expiry, fresh certificates and a new random incarnation alone do not solve this.

The operator-managed register is protected durable state outside the MySQL backup/restore set and outside tenant storage, with independently recoverable copies on a separate failure domain. It is a small restore-authorization register, not an online scheduler/command/quota store. Initially one recovery operator/tool owns updates under an exclusive stable OS lock, atomic file replacement plus file/directory fsync; concurrent coordinators across machines are unsupported and must be physically/access fenced. Its authenticity/protected distribution and signing/key recovery must be reviewed independently; no unreviewed key scheme is presumed approved. The Node Edge CA described in S-B1 must never sign restore attestations. Missing, inconsistent or unverifiable copies block recovery; never choose a lower epoch or reset to one.

Register v1 fields: `schemaVersion : int = 1`, `ControlPlaneRealmId : nonempty Guid`, `RecoveryEpoch : positive Int64`, `RestoreOperationId : Guid`, `PreviousRegisterDigest : sha256?` (null only at original initialization), `TargetCheckpointDigest : sha256`, `FenceBundleDigest : sha256`, `Phase : Preparing|Committed`, and authenticated operator/attestation reference. Realm identifies one control-plane authority lineage; epoch increments on each restore/authority recovery, not ordinary deployment or Node restart. Int64 is a strict decimal string on the wire. Overflow fails closed. Initial Node consumers require a provisioned register/realm; legacy behavior is not silently considered protected by it.

Add realm/epoch to Node activation/assignment/permit/command/result/recovery-grant/receipt, policy and route envelopes and Node journal activation/fence records. Evidence imports carry `OriginalControlPlaneRealmId`, `OriginalRecoveryEpoch` and the unchanged original tuple/digests, plus `ReportingControlPlaneRealmId`, `ReportingRecoveryEpoch` and current ReportingIncarnation. Recovery grants bind both sides; only explicit reviewed recovery can import across epochs/realms, and imported evidence never authorizes an old effect. They are required on all Node envelopes, included in canonical request/result digests, null only on explicitly legacy records that cannot dispatch to Node. N0-B's schema-v1 examples predate these additive **pre-implementation** fields; v1 implementers must use this consolidated required field set, never allow absence as an epoch-zero fallback. Node persists its pinned realm and highest epoch durably under the installation lock; ordinary authenticated commands cannot lower/replace them. No adoption of an unknown realm through a queue message or self-reported host identity. API/Worker/route writers must match restored DB metadata to the externally committed attestation before any mutation startup; unavailable register verification is ineligible, not an automatic bootstrap. Startup verification must read the designated current register authority (or an operator-controlled fresh recovery attestation bound to this startup), not accept a cached/backup signed file merely because its signature is valid. Old attestation replay and simultaneous old/new startup are explicit test cases. Read-only diagnostics may explain the block.

| Restore transition | Durable action / gate / crash behavior |
| --- | --- |
| R0: isolate | Stop admission and externally fence **all** pre-restore API/Worker/route writers, old Node/legacy managers, broker publication/consumption and installer/provider restart paths in the affected authority realm. Separate restored DB/network from the old writers. Settle already submitted engine/filesystem/route effects. Record per-host proofs; a partitioned/unreachable host blocks its scopes, and any host capable of shared/control-plane mutation blocks the entire restore. Revoking restored credentials alone is insufficient. |
| R1: prepare | Under register lock, reserve epoch E+1 with RestoreOperationId/checkpoint/fence hashes and Phase Preparing, fsync before opening restored DB to writers. Restore DB/data/artifacts/config/required keys into the isolated environment. Failure leaves quarantine; repeated same request resumes the same reserved epoch. A different attempt burns the reserved epoch and advances, never reuses it. |
| R2: reconcile | Reconstruct ownership, operation/dedup roots, reservations, CAP outbox and journal/physical-resource evidence since the checkpoint. Verify DB/data/artifact compatibility. Persist DB realm/epoch E+1 and recovery-only scopes; no publication. Restore old results only as original evidence. Lower restored counters are not treated as latest owner. |
| R3: commit authority | Commit the external register at E+1 after matching checkpoint/reconciliation/fence receipts, then permit only the recovery control plane to start. Crash before commit stays isolated; crash after commit with stale DB metadata blocks startup until matching reconciliation. No writer starts solely because DB claims E+1. |
| R4: rebind hosts | Through operator-authorized recovery bootstrap, each fenced host pins E+1 durably, activates a fresh incarnation in Recovering, advances affected assignment generations above all known maxima and imports old-epoch evidence using explicit grants. If maxima cannot be reconstructed, epoch separation still rejects every old-epoch effect; start new positive counters only within the new epoch, with explicit audit mapping. Counter order is lexicographic realm binding → epoch → incarnation/generation, not comparing generation alone. N0-B forbids reset within an epoch. |
| R5: verify and resume | Apply N0-C C4–C6 policy/storage/route/occupancy and single-owner proofs per scope. Unreachable hosts remain paused and cannot use old credentials on restored endpoints; they require physical fencing/rebind before resuming. An unfenced former control plane may not remain connected to them. Activate only verified scopes; retain blocked scopes and debt explicitly. |

This is an operationally enforced outage protocol, not automatic detection of arbitrary operator/database rollback. Unannounced rewind or cloning the register together with the DB is unsupported and invalidates safety claims. If register and all independent copies are lost, do not infer a safe epoch from the restored DB: quarantine, physically fence every prior writer/host and old trust endpoint, establish a new realm through reviewed disaster recovery, and explicitly re-enroll verified hosts. Lost/unreachable hosts remain disabled; no automatic placement over their local data. If comprehensive fencing cannot be proven, recovery cannot reopen mutation.

Restoring deduplication is a separate gate: changing epoch **does not** change N0-B's stable client key or turn an old request into a new intent. Lost postcheckpoint request roots/tombstones must be reconstructed from consistent DB/PITR/operation evidence, preserving original IDs and hashes. Node journals alone may not contain intake-pending requests, other Nodes' operations or external side effects. Per-scope completeness must be proven; otherwise API returns retryable 503 `restore_history_unknown` **before allocation** for new/replayed mutation requests in that scope, including apparently absent keys. Existing known keys can expose read-only historical status after authorization, not dispatch. CAP messages with old epoch are parked as historical evidence, never relabeled/reissued. Retirement watermarks cannot advance from a restored snapshot. Recovery may require forward repair or indefinite quarantine; no new key/namespace silently bypasses missing history.

Concrete restore example: checkpoint has epoch 2, generation 7 and no request K; before failure epoch 2/generation 9 executed K once. Operator fences all old writers, reserves/commits epoch 3, reconciles original K/root/result and occupancy, and rebinds the host. Delayed epoch-2 commands/results cannot mutate epoch-3 state, even if generation 7 reappears in restored MySQL. K returns its original root with no new allocation. If K's history coverage is unknowable, the account remains `restore_history_unknown`; restarting Node or rotating a certificate does not make it safe.

### Route ordering, policy units and capability gates

API `BackendRouteConfigService.RefreshAsync` reads eligible targets then writes configuration; current source uses a fixed temporary filename. `ManagedRuntimeRouteReconciliationService` invokes refresh at startup. That is source reuse, not proof of ordered multi-replica writes. Proposed N2-C protocol: one API-side route coordinator per configured destination, serialized across **every** writer with a stable OS-held lock on the supported shared route store; under that lock reread authoritative desired targets and the durable `(realm, epoch, RouteRevision, snapshot digest)`, render to a unique same-directory temporary file, flush/rename/directory-fsync, and retain applied readback/edge probe. Persist desired snapshot/revision in the existing deployment/routing authority before file effect; durable local applied watermark prevents replay of a lower epoch/revision. Crash after rename but before receipt reconciles exact digest; it cannot invent deployment success. Ordinary startup refresh uses the same gate. Old uncooperative writers are stopped/fenced before activation. A time-expiring DB lease without a locally enforced write gate is insufficient. Deployments lacking verified shared-lock semantics for a shared destination block route mutation; different destinations each need explicit serialized ownership and consistent desired snapshot. No cross-host lock service is introduced here.

Source/runtime separation remains logical source versus immutable deployed output (`live/` in the application contract, current/candidate artifact paths in Runner storage); do not rename physical trees or expose source/data/config/logs. PublishStatic exports only the validated public manifest to existing serving authority; Node volume names are never public roots. Candidate promotion requires current assignment/policy/revision, verified package/image digest and readiness; API finalization plus observed route is the success gate. Detailed public export/network/firewall and per-kind payload policies are N2/N3 specification gates before their consumers, not resolved by a generic envelope.

N0-C's explicit units are retained: CPU decimal cores; memory/storage/scratch/log limits Int64 bytes; PIDs/concurrency positive bounded integers; deadlines UTC. Provision source verifies `memory_mb * 1024 * 1024`; compatibility memory MB is MiB and maps through checked multiplication. XFS quota conversion must compare actual reported block units to bytes (no rounding a requested hard limit upward); other legacy fields require explicit adapter/unit tests before use. No unset limit becomes unlimited. Wire integer limits follow N0-B's lossless decimal-string rule for Int64; adapters reject overflow, unsupported precision and absent policy. Eligibility is an intersection of reviewed capability profile, current effective policy, fresh verified host inventory and approved trust cohort; null/unknown facts produce diagnostic/ineligible status. Liveness never implies capacity or privilege admission.
