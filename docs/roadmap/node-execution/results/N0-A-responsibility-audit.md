## End-to-end state and effect traces

These are source traces, not newly executed successful/interrupted operations.

1. **Provision:** authorized provisioning/bootstrap selects account policy → `PrepareProvisioningAsync` opens relational serializable admission, allocates account storage identity and persists Hosted/deployment intent → `DispatchPreparedProvisioningAsync` publishes provision request → Worker CAP subscriber calls `ManagedRunnerProvisionRequestedEventHandler`, claims dispatch and transactionally publishes infrastructure request → Infrastructure consumer validates identity and calls bundled allowlisted provisioning Action → Docker/storage/cgroup effect → authenticated result callback persists lifecycle outcome → enrollment/registration reconciliation confirms the Runner. Preparation and publication are distinct boundaries; never describe the whole host operation as one DB transaction. Duplicate dispatch and incomplete registration need the existing claim/reconciliation paths.
2. **Deploy/build/success:** authorized persisted `DeploymentOperation` → bounded API dispatcher/target attempt claim → `ApplicationDeploymentService` validates contract and target, obtains authorized Runner → package dispatch/download → Runner stages source and runs optional build → managed broker relay checks key, same-host Hosted binding and target attempt; derives resource/storage policy → Infrastructure executor inspects ownership, resolves immutable image and creates/builds candidate → Runner runtime manager probes/promotes → finalization synchronizes managed artifacts and routes → target/operation terminal result. A healthy promoted container alone is insufficient: artifact synchronization can fail afterward. Keep this partial success observable.
3. **Manual Action:** app access and `CanExecuteAppAsync` permission check plus fresh assigned Runner heartbeat → gateway persists module execution/protected RM request with stable execution identity → CAP publishes identity-only command → Runner HTTPS assignment, journal acceptance, module process execution and local result/log persistence → HTTPS terminal result projects to `AppModuleExecution` → broker acknowledgement. Logs/result reads authorize App before execution lookup; module artifacts use management queue.
4. **Scheduled Action:** API validates saved/enabled schedule → Worker polling claims due schedule → account row lock and transactional occurrence/reservation/publication → separate scheduled-action API CAP group revalidates occurrence and attaches execution → same Action path → terminal execution/occurrence reconciles. Worker-owned built-in maintenance instead uses registered trusted handler; it must not become arbitrary uploaded code execution.
5. **Files/tunnel:** App file controller (authenticated preview/private, published visibility/authentication policy for public routes) → assigned Runner resolver and transfer gateway → input artifact/protected RM operation → Runner assignment/download/write or read/upload → checked terminal result → API streams output and cleans it in `finally`. Tunnel requests instead use App policy/presence and the specific API instance's SignalR sender → Runner forwarder → response registry; they are not journaled file operations. Reconnect commands use durable management queues, but request streams remain ephemeral.
6. **Deletion:** existing app deletion authorization → `AppDeletionExecutionLock.AcquireAsync` → durable app claim or explicit supported interrupted recovery → claim/cleanup every assigned target with ownership assertions → delete app storage → remove App row. Failed recovery retains intent; recovery requires original executor stopped and compatible API versions. Host cleanup and DB deletion are not atomic and deleted data is not restored by retry.
7. **Interrupted RM operation:** `RunnerExecutionDeliveryHandler.HandleAsync` obtains authenticated assignment → `RunnerExecutionProcessor.ProcessAsync` locks operation, writes accepted marker before body → process dies after effect but before saved result → redelivery sees accepted/no terminal result and returns `Lost`, without repeating body → result saved locally → HTTPS `RunnerExecutionOperationService.ApplyAsync` transactionally persists protected terminal result/projection → local journal forgotten only after accepted API receipt → delivery acknowledgement. Crash after saved result/before receipt replays saved result; already-applied assignment skips effect. Cancellation before acceptance leaves tombstone; cancellation after acceptance reports potential effects. Existing `RunnerExecutionProcessorTests`/`RunnerExecutionDeliveryTests` and historical accepted-work interruption record support the design, not a new run at this HEAD.

## Persisted identities, secrets, mounts and resource boundaries

- Preserve account/user ID, App ID and deployment-target/environment ID independently of Runner/container identity. `HostedRunner` links User, RunnerHost, Runner, API key and specification revisions; `RunnerHost` links provider resource, Infrastructure Runner, approval/validation and storage facts. `DeploymentOperation`/attempt/candidate and module execution IDs are separate retry/ownership identities. Existing RM command/operation models do not establish the proposed Node incarnation + assignment generation + policy revision fence; N0-B must specify it rather than treating protocol v5 as that fence.
- `AccountStorageAllocation` is authority for account XFS project ID, storage RunnerHost ID and filesystem UUID; the host ID deliberately survives retirement without a foreign key. `HostedRunner.StorageProjectId` is a compatibility snapshot. A different host with free CPU is not an automatic valid destination. Preserve project ID/filesystem pair and quota ownership, not just directory bytes.
- Installer mounts Docker socket and host `/` at `/host`, uses privileged root, host PID and host network. It mounts protected config, workflows/workspace, artifacts and logs; persisted `api-key`, `installation-id`, profile, Runner config and broker settings are management secrets/state. Node privilege reduction is a new contract, not proven by replacing the process name or container with systemd.
- `FileStorageService` stores Runner execution journal and Hosted command result files alongside config; `RunnerExecutionOperation` protects request/result using API Data Protection. API replicas need compatible key rings and artifact storage. Broker credentials/queue permissions, Runner API keys, enrollment token, command-scoped secret grants and tenant Action secrets have distinct owners. No credential values were read for this audit. None belongs in tenant Node-managed workload environment except explicitly authorized tenant secrets.
- Bundled host implementation is `system-apps/automaton-infrastructure/actions/provision-hosted-runner/main.py`: `ensure_xfs_project_quota` and `verify_xfs_project_quota` validate project inheritance/enforcement, hard-limit readback and filesystem UUID; aggregate resource setup requires cgroup v2/systemd. Provisioning mounts the named system volume at `/automaton/system` and user volume at `/automaton/storage`, passes enrollment identity and uses a bounded writable layer, tmpfs/log policy and Hosted slice. The standard provisioning arguments do not mount the Docker socket. Actual UID/GID and image entrypoint permissions still need retained-host inventory. Its XFS fixture is `system-apps/automaton-infrastructure/tests/test_hosted_runner_storage_xfs_acceptance.py` (not run).
- `system-apps/automaton-infrastructure/actions/delete-hosted-runner/main.py` requires an explicit boolean `preserveVolumes`, verifies owned volumes and every discovered consumer before removing containers, and removes volumes only when false. This is useful existing behavior to preserve, but retirement still needs its own fenced adoption protocol.
- Managed app/build host operations use volume `automaton-hosted-runner-{HostedRunnerId:N}-user`, checked ownership labels and server-derived subpaths. `RunnerWorkspaceService` maps staged source to `workspace/runner/deployments/{app}/{target}/{attempt}/source`, candidate artifacts to `workspace/apps/{app}/targets/{target}/artifacts/candidates/{candidate}/application`, and durable data to `workspace/data/{app}/…`. Generic source/live separation and legacy script-layout compatibility remain distinct. Config/system/user volumes, actual mountpoints, UUIDs, project bindings and UID/GID must be inventoried per retained host in N0-C; naming is not sufficient adoption evidence.
- Runtime candidates mount application artifacts read-only and app data writable, use dropped capabilities/no-new-privileges, and optionally `--user`. Builds mount staged source writable, use bridge network and dropped capabilities. Both managed paths join `HostedRunnerResourceGroup.GetCgroupParent(HostedRunnerId)`. Current parent identity is Hosted Runner, not account Node ownership. Non-root defaults, actual aggregate controller enforcement, network isolation and management headroom cannot be proven from command arguments alone.
- Tenant Actions use `AppActionProcessExecutor` child processes and Runner scripting/workflow services; cancellation can kill Action process trees, while synchronous custom-step execution cannot promise forced cancellation. Bundled trusted Actions are a separate allowlist: provision/reprovision/restart/suspend/resume/delete Hosted Runner, measure storage and host validation. `TrustedInfrastructureActionExecutor` obtains bundled modules and scoped grants. Uploaded tenant modules must never inherit this host-management path.
- API published files/package store and Runner temp uploads/results are additional storage owners; neither should be conflated with XFS app durable data. Logs, journals, config, secret grants and runtime state must stay outside public roots. Explicit whole-app/Hosted deletion may destroy data; N4 executor retirement must not reuse that deletion operation unchanged.

## Support scope, remaining evidence and next slice

Current source supports managed standard brokered OCI runtime/builds, generic/direct Runner paths, manual/scheduled Actions, workflows/custom steps, file/media APIs, published output and BYO SignalR tunnels. Privileged Host approval and legacy controller paths are compatibility surfaces, not permission to carry tenant execution into Node. No current fleet inventory proves which profiles/cohorts are installed. Node migration and Linux systemd deployment compatibility are not implemented or accepted by this result. Windows/ARM, cross-host API artifacts, hostile multitenancy and automatic host-loss relocation have no new evidence here.

N0-A's source-only completion gate is satisfied: consumers have dispositions; successful and interrupted paths have concrete owners; automated coverage pointers, historical observations and unavailable host/live observations are separate. N0 as a whole remains pending. No runtime or Admin behavior changed, no schema/data changes occurred, and rollback of this slice is documentation-only. Do not infer binary/storage rollback compatibility for later migration.

The next smallest task is **N0-B identity and durable command ownership specification**, using this map and existing RM models. First define Node ↔ RunnerHost mapping, retained historical Runner references, enrollment/revocation/incarnation, account/target assignment generation, and the exact authorization/assignment/result fields on the existing transport. Include error/nullable rules, transactional keys and crash/effect/receipt ordering. Keep storage/cgroup/cutover mechanics in N0-C and roadmap-wide disposition in N0-D. N0-B must also explicitly classify BYO tunnels/files and tenant workflow/custom-step/Privileged Host compatibility before consumers are implemented; unsupported cases need deliberate errors rather than privileged fallback. No replacement runtime project is justified yet.

Three migration decisions remain open: (1) locally enforceable single-executor fencing and trusted command identity, (2) preservation of account XFS/volume/cgroup ownership without Hosted process identity, and (3) constrained execution/support scope for Actions and legacy/BYO consumers. These do not block N0-B specification; they block dependent implementation/cutover until resolved and independently reviewed.
