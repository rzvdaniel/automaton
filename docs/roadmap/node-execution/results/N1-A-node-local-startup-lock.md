# N1-A local startup and installation-lock specification

**Status:** implemented on `codex/n1a-node-startup-lock`; review and merge pending. **Baseline:** merged `main` at `fb252980a0bc28fb52562b11b151a376085c0ffa`, following PR #376 (`37d5169d` source, `949c0aee` acceptance evidence). This is the next bounded N1-A slice; it does not enable operational activation.

## Current owners and gap

`src/Automaton.Node/Preparation/NodePreparationHost.cs` builds an empty-configuration generic host; `NodePreparationService.cs` currently owns only process liveness and shutdown; `NodePreparationState.cs` exposes a process-local phase and permanently ineligible capabilities; `Program.cs` starts that preparation host. The Node project has no API, identity, journal, restore-register, HFA, broker, Docker, executor or host-effect client. `NodePreparationLifecycleTests.cs`, `NodePreparationDependencyTests.cs`, `NodeCapabilityValidatorTests.cs`, and `Automaton.Architecture.Tests/NodePreparationArchitectureTests.cs` own the current regression coverage. `docs/architecture/node-preparation.md` describes the implemented boundary.

There is no OS-held installation lock or startup gate. The local durable identity, journal, external restore-authority verifier, activation client, and recovery implementation are also absent and remain outside this slice. Therefore local startup cannot claim `RecoveryOnly` server authorization or `Active`; after lock acquisition the manager must remain locally `RecoveryRequired` and non-admitting until those owners exist.

## Contract

- The Node process requires the operator-supplied `AUTOMATON_NODE_HOST_STATE_DIRECTORY` setting. The setting is a non-secret absolute directory path passed explicitly into the host composition; it is not added as a general `IConfiguration` provider. No default or per-Node/account path is synthesized. The configured directory identifies the single host-wide manager authority location.
- This implementation supports Linux x64 only. Startup fails closed on other systems. The configured directory and every ancestor from `/` must already exist; each is opened relative to its already-open parent with `openat(O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC)` and validated through that handle as a root-owned directory with no group/other write permission before traversal continues. No `realpath` check followed by a separate path open is used. This prevents replacement of a checked component between validation and descent and rejects writable or symlinked ancestors even when the final directory is private. The initial filesystem allow-list is Linux ext-family, XFS, Btrfs, and tmpfs; all other filesystems fail closed until separately validated. The host lock file is a fixed name `node-manager.lock`; it must be a regular root-owned file with one link and mode `0600`. New files are created with mode `0600`; existing files are never truncated, removed, or replaced.
- Open the file with `O_NOFOLLOW | O_CLOEXEC` and take a nonblocking exclusive OS-held `flock(LOCK_EX | LOCK_NB)` on the stable inode. Verify the file descriptor's owner, mode, link count, file type and filesystem magic after opening. Keep the owning file handle open for the service lifetime. A second manager, invalid parent/file metadata, unsupported platform/filesystem behavior, or permission failure prevents the hosted service from starting. A missing lock file is created within the validated root-owned directory.
- Startup order is lock validation/acquisition, then local-state validation. Since this slice has no protected identity, journal, current external-register verifier, or API activation client, local state remains unavailable and the status becomes `RecoveryRequired`. This is a fail-closed liveness/diagnostic state, not `NodeManagement.Status`, an authenticated recovery session, or a grant to issue recovery requests. `CanAdmitWorkloads` stays false and capabilities remain unknown. No enrollment, identity creation, activation, realm/epoch mutation, network call, broker subscription, Docker access, executor, workload path, or other host effect is registered or run.
- Graceful stop marks the process stopped and releases the OS lock handle last. Repeated stop/dispose is safe. Cancellation before successful acquisition leaves no lock held. Abrupt process termination releases the kernel lock; the lock file and inode remain for the next process, which again starts `RecoveryRequired` and non-admitting. Lock ownership alone is not host fencing and does not prove old children, requests, legacy managers, or outstanding effects settled.
- The only long-lived state change in this slice is creation of the empty lock file when absent. Identity/journal/realm/epoch and activation persistence remain owned by their reviewed/later slices. Rollback never unlinks the shared lock file.

## Implementation and evidence

`NodePreparationService` now requires `INodeInstallationLock` before changing its process-local phase to `RecoveryRequired`; stop transitions to `Stopped` before releasing ownership. `NodeInstallationLock` uses Linux x64 `openat(O_NOFOLLOW|O_CLOEXEC)` and kernel `flock`, validates directory/file metadata and filesystem magic, and reports fixed failure codes without echoing paths. `Program` reads only the explicit host-state directory environment variable. The host still registers no API, broker, Docker, executor, workflow or host-effect adapters. `NodePreparationState.Capabilities.CanAdmitWorkloads` stays false. Since durable Node identity/journal and authority adapters do not exist, the local phase is explicitly not an authenticated `RecoveryOnly` session.

The lifecycle fakes verify cancellation after lock acquisition releases it, startup remains `RecoveryRequired`, and stop updates state before release. Linux host tests exercise separate manager processes, lock contention, abrupt holder death, unchanged device/inode on reacquisition, symlink/writable directories and ancestors (including a secure final directory beneath a group-writable parent), relative/missing paths, symlink/nonregular/hardlinked lock files and wrong owner. Directory traversal holds each parent handle while opening and validating its child. The existing compiled dependency test now allows only the narrow filesystem, native-lock and fixed diagnostic surface needed by this slice, while continuing to reject networking, child processes and execution-plane references.

## Named acceptance cases

1. `NodeHostLock_IsExclusiveAcrossIndependentProcesses`: against a disposable Linux local filesystem, two real Node manager processes share the configured host directory; exactly one acquires the kernel lock while the other fails closed. The winner retains the lock until stop.
2. `NodeHostLock_CrashReleasesHandleAndKeepsInode`: terminate the holder process; a new process acquires the lock and observes the same device/inode. It enters `RecoveryRequired`, with workload admission disabled.
3. `NodeHostLock_RejectsUnsafePathAndMetadata` and `NodeHostLock_RejectsSecureDirectoryUnderWritableAncestor`: reject missing/relative paths, symlinked directory components, a root-owned `0700` final directory below a group-writable ancestor, a symlink/non-regular/multi-link lock file, wrong owner, writable group/other modes, and unsupported OS/filesystem without registering subsequent services.
4. `NodeHostLock_CancelAndStopReleaseInOrder`: canceled startup acquires no lock; normal/repeated stop releases the handle; another real process then succeeds.
5. `NodeHostStartup_RemainsRecoveryRequiredWithoutIdentityAndAuthority`: after each successful lock acquisition, absent local identity/journal and absent reviewed external-register/API adapters keep startup non-admitting and produce only bounded fixed diagnostics.
6. `NodeHostDependencyGraph_HasNoOperationalEffects`: resolved hosted services and compiled references contain no broker, API/network client, Docker, process executor, tenant workflow/custom-step, or host-mutation adapter. Permit only the narrowly required filesystem/native-lock references and their direct runtime types.

Pure unit tests may cover path normalization and state transitions, but they do not count as process/lock or filesystem-ownership acceptance. The Linux process fixture is required for acceptance. No production/live host evidence is claimed.
