## Bounded first command and wire contract

The first command is `inspect-node-status-v1`: a bounded read of the already-persisted local Node identity, current activation receipt and startup phase. It does not inspect Docker, processes, filesystems, cgroups, storage, workloads or tenant data. Those observations and all resource reconciliation belong to N1-C. This command is read-only and has no host-effect adapter.

The durable command row is an extension of the existing `RunnerExecutionOperation` owner, not a second operation/quota ledger. It stores immutable canonical request bytes, SHA-256 digest, stable request-intent key, authenticated principal, creation/deadline, lifecycle state, exact terminal result bytes/digest and result receipt. For this Node-management command, the unique request key is `(RequestScopeKind=host, RequestScopeId=NodeId, RequestKind=inspect-node-status-v1, ClientRequestId)`. `ClientRequestId` is the unique-key component and is intentionally not repeated in the intent preimage. The exact `NodeCommandIntentV1` preimage is property-ordered compact UTF-8 JSON without BOM, insignificant whitespace or trailing newline: numeric `schemaVersion`, then `kind`, lowercase-D `nodeId`, lowercase-D `installationId`, and `view` (exactly `status`), using the same pinned .NET `System.Text.Json` web-default escaping as the command. Its SHA-256 is the intent digest. Generated `CommandId`, database timestamps, target epoch/incarnation/credential snapshot and outbox ID are excluded. In one transaction the API inserts/claims that unique key and stores the intent digest before generating a command ID or timestamps. Only the winning claimant creates canonical command bytes and its CAP outbox row in that same commit. A concurrent same-key/same-intent retry returns the exact existing command bytes and outbox identity; same-key/different-intent is conflict. A pre-commit failure creates neither claim nor command/outbox. Tenant workload commands later use N0-B's account-scoped stable intent key claimed before allocation; generated workload, placement and incarnation values are excluded from that key.

The version-1 command contract has the following required fields. Commands/results are UTF-8 JSON without BOM, insignificant whitespace or a trailing newline. Properties are serialized in declared order using the .NET `System.Text.Json` web defaults pinned by the contract version; strings use the default JSON escaping; GUIDs use canonical lowercase `D` form; SHA-256 values are lowercase 64-character hex; positive `Int64` values are canonical decimal strings. Duplicate/unknown properties, invalid enums, trailing bytes and any byte sequence that does not equal reserialization are rejected before journal or handler invocation. The SHA-256 request digest is calculated over the canonical command bytes with the `requestSha256` property omitted; the full command is then serialized with `requestSha256` last. Command and terminal-result decoded bodies are each bounded at 1 MiB, broker wake-up bodies at 4 KiB, and inline diagnostic text at 64 KiB, matching N0-B's v1 limits. Larger evidence must use the existing authorized artifact path, never an expanded broker body.

Command timestamps are UTC RFC 3339 with exactly seven fractional digits and `Z`. The API authors `issuedAtUtc` and `deadlineUtc` from its authoritative database UTC clock. Node validates both against its UTC wall clock: `issuedAtUtc` may be at most 30 seconds in the receiver's future; `deadlineUtc` must be after Node's current UTC wall time and no later than five minutes after issue time. No late-delivery grace is applied: an expired command is rejected before journal/handler; API resolves it as expired. `NodeStatusResultV1.observedAtUtc` is the Node wall-clock observation time, not a server receipt/completion time. It uses the same exact UTC syntax, must be no earlier than `issuedAtUtc - 30 seconds`, no later than `deadlineUtc`, and no later than API receive time plus 30 seconds. API `receivedAtUtc` and `completedAtUtc` are server-generated fields in the receipt and cannot be supplied by Node. `receivedAtUtc` comes from the authoritative API/database UTC clock; a monotonic clock may be used only for elapsed-duration checks. Reject offsets, missing/excess fractional digits, invalid calendar values, observed times before the allowed issue bound, after the command deadline, or more than 30 seconds ahead of server receive time.

## Authorization, journal and recovery rules

The API listener must authenticate both the pinned Node certificate forwarded over an authenticated Traefik backend connection and the Node API key, then derive NodeId/InstallationId/realm from the current durable binding. The command endpoint checks the exact active credential revision, enrollment status, current realm and freshly verified external recovery epoch. A valid Node certificate, API key, queue name or message body alone does not grant command authority. The command's canonical digest includes every authorization and recovery field. Queue permissions are exact-node and consume-only for Node command queues; foreign Node publish/consume, default-exchange escape, configure/write privileges and legacy Runner queues are denied. Broker reconnection revalidates the authenticated Node binding before consuming again.

The Node journal is a versioned extension to the protected installation state store. Each record is protected by the already-held installation lock and stores exact command bytes/hash and tuple, current phase, result bytes/hash, API receipt and broker-delivery acknowledgement. Durable transitions are `Validated -> Accepted -> ResultPending -> ResultReported`; no handler runs before `Accepted` is atomically persisted. `ResultPending` is atomically persisted before HTTP reporting; result retries send byte-identical bytes. The wake-up remains unacknowledged until the matching API result receipt is validated and its exact bytes plus receipt are durably journaled as `ResultReported`. Only then may the notification be acked. An API timeout, connection loss, unknown response, mismatched receipt or failed journal fsync leaves the notification unacked and the result pending; redelivery/readback retries the same immutable result. A crash after `Accepted` but before the read-only status handler completes may re-run only this explicitly replay-safe handler after revalidating fresh identity and authority. A crash after result persistence replays the exact saved bytes and never invokes the handler again. Do not synthesize a new result or command.

Any future effect-capable command must use a separate explicitly authorized effect state machine: persist intent before effect, record effect evidence before result, and on crash after possible effect mark `Uncertain`/occupied. It must reconcile observable ownership or retain the block; never blindly re-execute. N1-B's first command has no such effect and cannot imply this future gate is passed.

Commands are valid only for their pinned realm, freshly verified positive RecoveryEpoch, target Node/installation, current credential revision and positive incarnation. This first read-only command requires the N0-B RecoveryOnly management grant and never runs on a Node that has only local `RecoveryRequired` status without that grant. `Created`, `RecoveryRequired`, and `Stopped` are local `NodePreparationPhase` values, not server lifecycle statuses. A command can execute only in a running process that holds the installation lock, has reached local `RecoveryRequired`, and passes the RecoveryOnly grant and current identity/authority validators. `Created` is pre-initialization; `Stopped` means the process has stopped and cannot execute. The result's `startupPhase` is exactly `RecoveryRequired`; the command does not introduce a new preparation phase or imply `Active`. A lab fixture may provide synthetic grant material through the production verifier and binding checks, but production composition has no test grant issuer and remains unable to consume. Old commands cannot be relabeled to a new incarnation. Cross-incarnation saved-result import is not part of this status-command slice; N0-B's recovery grant/evidence schema is owned by N1-C reconciliation and must preserve the original command tuple/hash/result bytes while separately recording the reporting identity. Such evidence is historical and cannot authorize an effect. Missing, stale, cloned or unavailable external-register proof leaves startup quarantined.

The isolated fixture can use synthetic Node/HFA/register signers only through the same parser, verifier and binding interfaces used by production. Test-only services live in test assemblies and are absent from production DI. They can establish validator behavior, not issuer custody, authority freshness in deployment or physical host fencing. Production composition remains fail-closed and startup remains `RecoveryRequired` until separately reviewed authority adapters and operational evidence exist.
