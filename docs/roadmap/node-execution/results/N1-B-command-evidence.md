## Bounded first command and wire contract

The first command is `inspect-node-status-v1`: a bounded read of the already-persisted local Node identity, current activation receipt and startup phase. It does not inspect Docker, processes, filesystems, cgroups, storage, workloads or tenant data. Those observations and all resource reconciliation belong to N1-C. This command is read-only and has no host-effect adapter.

The durable command row is an extension of the existing `RunnerExecutionOperation` owner, not a second operation/quota ledger. It stores immutable canonical request bytes, SHA-256 digest, stable request-intent key, authenticated principal, creation/deadline, lifecycle state, exact terminal result bytes/digest and result receipt. For this Node-management command, the unique request key is `(RequestScopeKind=host, RequestScopeId=NodeId, RequestKind=inspect-node-status-v1, ClientRequestId)`. `ClientRequestId` is the unique-key component and is intentionally not repeated in the intent preimage. The exact `NodeCommandIntentV1` preimage is property-ordered compact UTF-8 JSON without BOM, insignificant whitespace or trailing newline: numeric `schemaVersion`, then `kind`, lowercase-D `nodeId`, lowercase-D `installationId`, and `view` (exactly `status`), using the same pinned .NET `System.Text.Json` web-default escaping as the command. Its SHA-256 is the intent digest. Generated `CommandId`, database timestamps, target epoch/incarnation/credential snapshot and outbox ID are excluded. In one transaction the API inserts/claims that unique key and stores the intent digest before generating a command ID or timestamps. Only the winning claimant creates canonical command bytes and its CAP outbox row in that same commit. A concurrent same-key/same-intent retry returns the exact existing command bytes and outbox identity; same-key/different-intent is conflict. A pre-commit failure creates neither claim nor command/outbox. Tenant workload commands later use N0-B's account-scoped stable intent key claimed before allocation; generated workload, placement and incarnation values are excluded from that key.

The version-1 command contract has the following required fields. Commands/results are UTF-8 JSON without BOM, insignificant whitespace or a trailing newline. Properties are serialized in declared order using the .NET `System.Text.Json` web defaults pinned by the contract version; strings use the default JSON escaping; GUIDs use canonical lowercase `D` form; SHA-256 values are lowercase 64-character hex; positive `Int64` values are canonical decimal strings. Duplicate/unknown properties, invalid enums, trailing bytes and any byte sequence that does not equal reserialization are rejected before journal or handler invocation. The SHA-256 request digest is calculated over the canonical command bytes with the `requestSha256` property omitted; the full command is then serialized with `requestSha256` last. Command and terminal-result decoded bodies are each bounded at 1 MiB, broker wake-up bodies at 4 KiB, and inline diagnostic text at 64 KiB, matching N0-B's v1 limits. Larger evidence must use the existing authorized artifact path, never an expanded broker body.

Command timestamps are UTC RFC 3339 with exactly seven fractional digits and `Z`. The API authors `issuedAtUtc` and `deadlineUtc` from its authoritative database UTC clock. Node validates both against its UTC wall clock: `issuedAtUtc` may be at most 30 seconds in the receiver's future; `deadlineUtc` must be after Node's current UTC wall time and no later than five minutes after issue time. No late-delivery grace is applied: an expired command is rejected before journal/handler; API resolves it as expired. `NodeStatusResultV1.observedAtUtc` is the Node wall-clock observation time, not a server receipt/completion time. It uses the same exact UTC syntax, must be no earlier than `issuedAtUtc - 30 seconds`, no later than `deadlineUtc`, and no later than API receive time plus 30 seconds. API `receivedAtUtc` and `completedAtUtc` are server-generated fields in the receipt and cannot be supplied by Node. `receivedAtUtc` comes from the authoritative API/database UTC clock; a monotonic clock may be used only for elapsed-duration checks. Reject offsets, missing/excess fractional digits, invalid calendar values, observed times before the allowed issue bound, after the command deadline, or more than 30 seconds ahead of server receive time.

## Authorization, journal and recovery rules

The API listener must authenticate both the pinned Node certificate forwarded over an authenticated Traefik backend connection and the Node API key, then derive NodeId/InstallationId/realm from the current durable binding. The command endpoint checks the exact active credential revision, enrollment status, current realm and freshly verified external recovery epoch. A valid Node certificate, API key, queue name or message body alone does not grant command authority. The command's canonical digest includes every authorization and recovery field. Queue permissions are exact-node and consume-only for Node command queues; foreign Node publish/consume, default-exchange escape, configure/write privileges and legacy Runner queues are denied. Broker reconnection revalidates the authenticated Node binding before consuming again.

The Node journal is a versioned extension to the protected installation state store. Each record is protected by the already-held installation lock and stores exact command bytes/hash and tuple, current phase, result bytes/hash, API receipt and broker-delivery acknowledgement. Durable transitions are `Validated -> Accepted -> ResultPending -> ResultReported`; no handler runs before `Accepted` is atomically persisted. `ResultPending` is atomically persisted before HTTP reporting; result retries send byte-identical bytes. The wake-up remains unacknowledged until the matching API result receipt is validated and its exact bytes plus receipt are durably journaled as `ResultReported`. Only then may the notification be acked. An API timeout, connection loss, unknown response, mismatched receipt or failed journal fsync leaves the notification unacked and the result pending; redelivery/readback retries the same immutable result. A crash after `Accepted` but before the read-only status handler completes may re-run only this explicitly replay-safe handler after revalidating fresh identity and authority. A crash after result persistence replays the exact saved bytes and never invokes the handler again. Do not synthesize a new result or command.

Any future effect-capable command must use a separate explicitly authorized effect state machine: persist intent before effect, record effect evidence before result, and on crash after possible effect mark `Uncertain`/occupied. It must reconcile observable ownership or retain the block; never blindly re-execute. N1-B's first command has no such effect and cannot imply this future gate is passed.

Commands are valid only for their pinned realm, freshly verified positive RecoveryEpoch, target Node/installation, current credential revision and positive incarnation. This first read-only command requires the N0-B RecoveryOnly management grant and never runs on a Node that has only local `RecoveryRequired` status without that grant. `Created`, `RecoveryRequired`, and `Stopped` are local `NodePreparationPhase` values, not server lifecycle statuses. A command can execute only in a running process that holds the installation lock, has reached local `RecoveryRequired`, and passes the RecoveryOnly grant and current identity/authority validators. `Created` is pre-initialization; `Stopped` means the process has stopped and cannot execute. The result's `startupPhase` is exactly `RecoveryRequired`; the command does not introduce a new preparation phase or imply `Active`. A lab fixture may provide synthetic grant material through the production verifier and binding checks, but production composition has no test grant issuer and remains unable to consume. Old commands cannot be relabeled to a new incarnation. Cross-incarnation saved-result import is not part of this status-command slice; N0-B's recovery grant/evidence schema is owned by N1-C reconciliation and must preserve the original command tuple/hash/result bytes while separately recording the reporting identity. Such evidence is historical and cannot authorize an effect. Missing, stale, cloned or unavailable external-register proof leaves startup quarantined.

The isolated fixture can use synthetic Node/HFA/register signers only through the same parser, verifier and binding interfaces used by production. Test-only services live in test assemblies and are absent from production DI. They can establish validator behavior, not issuer custody, authority freshness in deployment or physical host fencing. Production composition remains fail-closed and startup remains `RecoveryRequired` until separately reviewed authority adapters and operational evidence exist.

#### Legacy Runner isolation and row shape

Sharing the table is conditional on explicit role isolation in the same implementation slice. A legacy Runner row has `NodeRecordRole IS NULL` and every other Node extension column null. A Node row has `NodeRecordRole IN ('RequestIntent','Command')`; it keeps legacy `ResultJson`, `CompletedAtUtc` and `CancellationRequested` null/false, and those legacy fields are never its lifecycle authority. Node state, canonical result and receipt live only in the Node extension columns. Required legacy columns (`Id`, `RunnerId`, `RequestedByUserId`, `ProtectedRequest`, `CreatedAtUtc`) remain populated for schema compatibility, but legacy code must treat the role discriminator as mandatory isolation.

Every existing Runner-only read or write against this table must add `NodeRecordRole IS NULL` before rollout of Node rows: operation lookup by ID, assignment and result authorization, cancellation, retry/replay, capacity and pending-work queries, Runner revocation/termination, and any bulk terminalization. Predicate by `RunnerId` or `CompletedAtUtc` alone is insufficient. Node endpoints and reconciliation queries must require the expected non-null role and exact Node tuple; a missing/unknown role fails closed. Package cleanup must derive active Runner transfer artifacts only from rows satisfying `NodeRecordRole IS NULL AND CompletedAtUtc IS NULL`; Node rows do not represent transfer artifacts. This is a required code isolation boundary, not an assumption that the current unfiltered generic queries are already safe. If any legacy caller cannot be made role-aware in its owning slice, Node rows must use a separate owner/table instead of this shared table.

`RunnerCompatibilityAndNodeRowIsolation` is required alongside the migration test. Seed legacy Runner operations plus Node root/command rows for the same transport Runner ID. Exercise each affected Runner query, assignment/result/cancellation/revocation path and package-cleanup selection; assert it reads or mutates only legacy rows, while Node `NodeState`, result bytes, receipt bytes and null legacy lifecycle fields remain unchanged. Then exercise Node lookup and assert it ignores legacy rows. Run existing Runner cancellation, result replay, queue-capacity and transfer-cleanup regressions unchanged to prove Runner semantics remain intact. This is mandatory because a shared table without role predicates can let Runner revocation terminalize Node work or package cleanup retain/delete artifacts based on Node rows.

### Administrator admission endpoint

The first status command is admitted through `POST /api/nodes/{nodeId}/management-commands/inspect-status` on the ordinary authenticated API listener, protected by the existing administrator host-management authorization. This is an ordinary administrator operation, distinct from the Node-authenticated management routes; it is never accepted on the Node-management or bootstrap listener. Classify it in the ordinary-listener allow-list as an explicit administrator route. The closed request has ordered properties `schemaVersion`, `clientRequestId`, `view`; `schemaVersion` is numeric `1`, `clientRequestId` is required lowercase-D GUID and `view` is exactly `status`. The caller cannot submit realm, installation, incarnation, credential, policy, command ID, deadline, queue, result, or host-effect fields. The server resolves and authorizes the Node binding and creates the immutable command/outbox from current state.

The first committed response is `202` with canonical `NodeCommandAdmissionV1` fields `schemaVersion`, `requestOperationId`, `commandId`, `status`, `requestIntentSha256`; `status` is the immutable `Admitted`. A same-key/same-intent retry returns `200` with byte-identical admission receipt bytes. Reuse with different normalized intent is `409 idempotency_conflict`. Missing key or malformed body is `400 invalid_contract`; unauthenticated/unauthorized caller is `401`/`403`; unknown or inaccessible Node is masked `404 not_found`; transient failure before commit is `503 temporarily_unavailable`. Caller retries after timeout reuse the exact client key/body. Before commit, no root/command/outbox survives; after commit, retry returns the same admission receipt without another command, outbox, reservation or workload.

`NodeCommandAdmissionListenerAndIdempotency` asserts that this exact endpoint is served only on the ordinary API listener, has no mapping on management/bootstrap listeners, authorizes the actual account/host owner, and rejects all caller-supplied binding or executor fields. Its independent-context MySQL race submits the same key/body and changed-body key; exactly one root, command and outbox commit, replay IDs/bytes match, and changed intent is conflict. Faults before commit leave zero durable rows; lost response after commit returns the same admission receipt.

### Conditional result/expiry commit and loser readback

The result and expiry transitions compete on the same command row, with MySQL UTC as the sole deadline clock:

- Result commit is one conditional update from `Queued` to `ResultStored`. Predicates include `Id`, `NodeState='Queued'`, bound `NodeId`, `NodeInstallationId`, realm, recovery epoch, incarnation, credential revision, `NodeDeadlineUtc > UTC_TIMESTAMP(6)`, and null result/receipt columns. The transaction first locks and validates the current NodeManagement binding; revocation and result reporting use the same NodeManagement-before-operation lock order. Exactly one affected command row wins. Exact result bytes/hash, immutable receipt bytes/hash and completion timestamp are written together.
- Expiry is one conditional update from `Queued` to `Expired` where `NodeDeadlineUtc <= UTC_TIMESTAMP(6)` and result/receipt fields are null. It writes no result and cannot overwrite `ResultStored`. Exactly one affected row wins. Both statements evaluate the deadline in the database and rely on the row's conditional state transition, so result-versus-expiry has one terminal winner.
- An update affecting zero rows is never treated as success. Read the row again in a fresh context/transaction, reauthorize the caller against current NodeManagement, and branch only on durable state: byte-identical `ResultStored` returns its saved receipt; different result bytes return conflict; `Expired` returns terminal expiry; missing/foreign rows remain masked as not found; a still-queued row is retryable only after the winning transaction is confirmed rolled back or the caller's transaction has ended. No lost response creates a second receipt, timestamp or ID.

`NodeCommandResultExpiryCasRace` uses two independent MySQL contexts and synchronizes concurrent result and expiry attempts on both sides of the database deadline. It asserts exactly one state transition, one immutable receipt only for the result winner, no overwritten result, and a loser response derived from a fresh-row read. It also injects rollback before commit and confirms a retry can win once; lost HTTP response followed by byte-identical PUT/readback returns the original receipt bytes. Boundary cases at database time exactly equal to the deadline resolve to `Expired` because result requires `>` and expiry requires `<=`.

### HTTP status, body and retry contract

All API error bodies are canonical `NodeCommandErrorV1` JSON with the exact ordered fields `schemaVersion`, `code`, `commandId`, `retryAfterSeconds`; nulls are emitted. `code` is a closed enum, `commandId` is null when disclosure is unsafe, and `retryAfterSeconds` is null except for retryable responses. Error bodies contain no query, identity, secret or database details. `Retry-After` and `retryAfterSeconds` agree and are bounded to 1–60 seconds.

| Route/outcome | HTTP and body | Node action |
| --- | --- | --- |
| `GET /commands/{id}` — current authorized queued command, read from the primary/strongly consistent owner | `200` with exact canonical command bytes. | Validate and durably journal before handler invocation. |
| Fetch — command expired or already terminal | `410 command_expired` or `409 command_terminal`; expiry is durably CAS-settled before returning 410. | Persist terminal rejection without handler and ack only after durable journal record. |
| `GET /commands/{id}/result-receipt` — receipt committed | `200` with exact saved receipt bytes. | Validate and fsync receipt, then mark reported and ack. |
| Receipt read — result still pending | `202`, `code=result_pending`, retry after 1 second. | Keep immutable local result pending; retry receipt read/identical PUT; do not ack. |
| First valid result PUT | `201` with exact newly stored receipt bytes. | Validate and fsync receipt, then ack. |
| Byte-identical result PUT replay | `200` with byte-identical original receipt. | Validate and fsync receipt, then ack. |
| Unknown or foreign command/receipt | `404`, `code=not_found`, no identity disclosure. | Persist a bounded rejected-wakeup journal record without running a handler; ack only after that record is durable. |
| Stale incarnation/epoch tuple, conflicting bytes or already-terminal incompatible state | `409`, closed codes `binding_conflict`, `result_conflict`, or `command_terminal`. | Preserve any result; journal/quarantine the mismatch; never run or regenerate a result. Ack only after durable quarantine; require fresh authorization before resuming. |
| Expired command with no result | `410`, `code=command_expired`. | Persist terminal rejection without handler and ack only after durable journal record. |
| Malformed/noncanonical command or result | `422`, `code=invalid_contract`. | Quarantine exact bounded input, do not invoke handler; ack only after durable rejection record. |
| Missing/invalid authentication or revoked binding | `401`/`403`, `code=authentication_required`/`authorization_denied`. | Keep command/result quarantined and unacked; stop that consumer session pending current credentials/authority. |
| Database/external-authority/service transient failure | `503`, `code=temporarily_unavailable`, retry after 1–60 seconds. | Keep the wake-up unacked and retry with the identical request/result bytes. |
| Rate limit | `429`, `code=rate_limited`, retry after 1–60 seconds. | Keep the wake-up unacked and retry unchanged after the interval. |

The API masks unknown and foreign IDs identically. It reauthorizes before returning any existing body/receipt, including an idempotent replay. A command, its CAP outbox event and stable root commit atomically, so a fetch never needs to poll for a separately committed claim; command fetch uses the primary/strongly consistent owner. Node retries `202` only for receipt readback while a queued command is still unsettled, plus `429`, `503`, transport timeout/connection loss and `5xx`, using bounded exponential backoff capped at 60 seconds and identical bytes. It does not retry a changed request after `409`, a malformed payload after `422`, or an expired command after `410`. `401`/`403` never authorize fallback; they stop the consumer and preserve the journal for a fresh authenticated recovery session. The broker wake-up is acknowledged only after a durable result receipt or the explicit pre-handler `Rejected`/`Quarantined` journal state above; no uncommitted local rejection can drop a delivery.

Required deterministic/API tests are `NodeCommandHttpOutcomeMatrix` (each row above, exact status and canonical bytes, retry headers, error-code closure, masked foreign identity, and handler invocation count zero on every rejection), `NodeCommandReceiptLostResponse` (201 then lost response, identical PUT and receipt GET produce original receipt bytes), and `NodeWakeupAckRequiresDurableOutcome` (fault before journal fsync keeps delivery unacked; after durable terminal rejection it may ack; after transient API error it cannot ack). The MySQL tests must additionally assert the role/nullability/index shape, actual result-versus-expiry SQL affected-row behavior, revocation/result race, exact duplicate replay and stale/foreign loser readback. These are mandatory before the stateful N1-B consumer is accepted.
