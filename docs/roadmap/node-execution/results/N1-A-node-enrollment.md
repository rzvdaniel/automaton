## Specification before implementation

Add dedicated `src/Automaton.Node` executable and `Automaton.Node.Tests`, with only Microsoft generic-host infrastructure. No Runner reference, shared-RM extraction, credentials/config binding, networking client/server, broker consumer or engine probe. Program starts an empty-config generic host with one preparation lifecycle service; it reports constant preparation-only diagnostics, waits for shutdown and honors cancellation. Its process-local phase Created/Running/Stopped is liveness only, never ownership/admission. No durable state exists. Do not install a service or package an operational Node.

Pure capability input contains nullable OS, architecture, engine/version, cgroup mode and nullable storage observations (volume GUID, filesystem UUID/type, nullable XFS project ID). Missing/unsupported fields remain unknown/ineligible; supplied facts are synthetic/unverified. Supported syntax is Linux/x64/Docker/cgroup v2/XFS, with nonempty volume/filesystem GUIDs and positive project IDs. Text is bounded to 128 characters with no control characters; at most 64 storage observations; duplicate volume IDs invalid, repeated quota domains allowed because alias volumes may share a project. Reject excess before scanning/copying. Diagnostics are a finite enum, never raw input. Accepted facts are copied into read-only snapshots. Even a complete valid report has no eligible workload kinds and cannot authorize admission in this skeleton.

Lifecycle tests cover start/stop, cancellation before start and during run, repeated shutdown, terminal stop state and no credential/config/argument input or raw capability echo in logs. Capability tests cover missing/unsupported/null/invalid IDs/control characters/oversized strings and arrays, same-project aliases and defensive copying. Architecture tests enforce project/transitive dependency allowlists, package boundary, no tenant/legacy hosted services in resolved DI and no accidental operational Node types/registrations.

The narrow future `Automaton.Execution.Management` boundary is defined in [Node preparation architecture](../../../architecture/node-preparation.md). It will share existing RM mechanics only when real consumers require extraction under reviewed N1 contracts. No empty library, transport duplicate or changed Runner behavior is introduced. New projects belong in Automaton.All.sln; all analyzer thresholds stay unchanged. Existing architecture-project baseline is captured before edits; new projects have no preexisting symbols/diagnostics, so build their scaffolds before adding C# sources; the empty executable is intentionally not yet runnable.
