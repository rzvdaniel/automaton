# N0 authentication selection and security-contract review

Recorded 2026-10-12 against the post-merge `origin/main` containing PR #371 (`5589e31de51f4a631c5d707b8af2b9433c66e70e`), which the user reviewed as a design proposal. This is a documentation-only operational decision and author review of N0-B/N0-C/N0-D. It is not an independent security approval, implementation, TLS/proxy configuration, deployment, or live acceptance.

## Authentication selection

**Selected design proposal for Node v1: mutual TLS client proof plus the existing Node-bound API key on every authenticated Node management HTTPS request.** The API key remains the database authorization principal; the client certificate proves possession of a separately enrolled installation key. The API must bind both to the same active Node, installation, credential revision, control-plane realm/recovery epoch and current authorization state. Neither factor alone authorizes a Node request. Each Node installation creates a self-signed ECDSA P-256 client certificate locally. There is no shared Node certificate authority, issuer service, or issuer private key to hold, back up, or recover. The authorized enrollment record pins the CSR public-key SHA-256 fingerprint. Bootstrap carries the signed CSR and its matching self-signed leaf; the API verifies proof of possession/key equality and stores the exact leaf-certificate SHA-256 fingerprint as the active identity. The self-signature or certificate subject alone is not trusted. The only pre-certificate exception is a tightly scoped enrollment bootstrap endpoint on a **separate configured bootstrap hostname** with server-authenticated TLS. It accepts a one-use enrollment token and signed CSR/certificate, consumes only the already authorized/pinned enrollment and returns its receipt; it cannot activate, fetch assignments, submit results, consume broker messages or cause host effects. It must not weaken the dedicated mTLS management hostname. Broker credentials remain separate, narrowly scoped queue credentials and are not replaced by TLS identity.

This settles the mechanism and the proposed operational model to take through review; it does **not** approve implementation. Per-Node key protection, API/proxy identity keys, rotation/revocation and network isolation remain operational work. Those choices and the contract require independent security/operations review before enrollment or activation code is enabled. No bearer-only fallback is allowed. RFC 8705 is a design reference for certificate-thumbprint binding, not a claim that Automaton uses its OAuth flow. Traefik documents `RequireAnyClientCert` for requiring a presented certificate without CA-chain validation, `PassTLSClientCert` for forwarding its PEM, and `ServersTransport` client certificates and backend trust roots; Automaton's API must perform the exact fingerprint/authorization checks described below. [RFC 8705](https://www.rfc-editor.org/rfc/rfc8705.html), [Traefik client-auth options](https://doc.traefik.io/traefik/reference/routing-configuration/http/tls/tls-options/), [PassTLSClientCert](https://doc.traefik.io/traefik/master/reference/routing-configuration/http/middlewares/passtlsclientcert/), and [ServersTransport](https://doc.traefik.io/traefik/reference/routing-configuration/http/load-balancing/serverstransport/) describe the relevant mechanisms. The deployed Traefik configuration and edge path were not probed.

## Operational decisions

### Node certificate issuer and key recovery

The Node installation generates its key, self-signed client certificate and signed CSR locally. The installer displays the public-key SHA-256 fingerprint; an authenticated administrator or BYO account owner enters that value when creating the scoped one-use enrollment. Bootstrap verifies the CSR signature, certificate self-signature, equality with the preapproved public key and exact scope, then binds the certificate thumbprint. The control plane never signs the Node certificate. Platform Operations owns the enrollment policy and re-enrollment runbook, not a Node certificate signing key. Node private keys remain in protected installation state, readable only by the trusted Node service identity. They are not copied to the control plane, included in database or host backups, or escrowed centrally. If a key or local state is lost, Operations first proves/fences the old manager and host ownership, then an administrator/owner creates a new one-use enrollment pinned to a new key. The old identity is revoked; it is never recovered by copying a key or replaying the old token.

The Node certificate validity is **90 days maximum**. The Node starts an authorized rotation after 60 days, leaving a 30-day completion window. Rotation prepares and proves the new certificate while the current cert is still active; commit atomically pins the new fingerprint/revision and invalidates the old certificate. API checks exact fingerprint, active revision, self-signature, `NotBefore`/`NotAfter` and the maximum lifetime on every Node request. An expired certificate cannot renew itself; recovery requires the fenced enrollment procedure. This makes certificate expiry meaningful even though the certificate is self-signed. The validity and overlap are design values for independent review, not runtime settings already deployed.

### Traefik-to-API identity and certificate forwarding

Use a dedicated **Automaton Node Edge CA** only for the Traefik backend-client certificate and API blue/green backend-server certificates. It does not issue Node certificates. Traefik authenticates to each dedicated HTTPS Node listener with a CA-issued client certificate carrying the fixed URI SAN `urn:automaton:traefik:node-ingress`; each API color verifies chain, client-auth EKU, that exact SAN and the active leaf fingerprint. Each API color presents a separate CA-issued server certificate with the configured internal service DNS SAN and server-auth EKU. Traefik's dedicated `ServersTransport` presents its client cert, verifies the API certificate chain against the public Edge CA certificate, checks the configured server name, and leaves `insecureSkipVerify` false. No subject common name is used as authorization.

At the public edge, the dedicated Node-management SNI option requires a client certificate (`RequireAnyClientCert`), which requires a certificate but does not validate a CA chain. Traefik first removes any inbound `X-Forwarded-Tls-Client-Cert` header using the Headers middleware, then `PassTLSClientCert` writes the PEM from the actual TLS peer. The API parses exactly one bounded leaf certificate, verifies its validity and exact active Node fingerprint from the database, and also requires the Node-bound API key. Traefik's frontend need not trust a Node CA; the exact DB pin is the Node identity check. The API accepts this header only on the dedicated listener after backend mTLS has authenticated the Traefik certificate. It ignores subject/issuer text and ordinary `X-Forwarded-*` values for Node identity.

**Issuer and key custody:** Platform Operations Security Custodians own the Edge CA signing key. The offline ECDSA P-256/SHA-256 CA certificate is valid for ten years; the Traefik client and API color server certificates are valid for 365 days and rotate 30 days before expiry. Keep the CA key offline and outside the production host, repository, application database and Node installations. Issue only the three service certificates above (one Traefik client identity and one API server identity per color); do not mount the CA signing key into Traefik or API. Store the CA private key encrypted on two offline recovery copies in separate access-controlled locations; key use or recovery requires two designated custodians and a logged procedure. Store the public CA certificate and leaf fingerprints with protected deployment configuration. Leaf private keys stay in their individual service secret sources and are not backed up; loss means regenerate/reissue and update trust. CA-key loss uses the verified offline copy; if no copy validates, create a new CA and rotate all service certificates. Suspected CA compromise requires trust-root replacement and full leaf reissue, never restoration of the compromised key. A named custodian pair, offline media locations and recovery drill must be assigned before enrollment; the repository does not establish that these operational controls currently exist.

The existing Compose file has no secret declarations. Before use, add deployment-managed, file-backed secrets for Traefik/API leaf keys, readable only by the relevant service identity and mounted read-only; the Edge CA signing key remains offline. Verify source-file permissions and container UID access. Traefik's backend client identity is authorized by its exact leaf SHA-256 fingerprint on both API colors, in addition to Edge-CA chain, client-auth EKU and URI SAN checks. A replacement CA root alone does not authorize a replacement client leaf. For Traefik client-certificate rotation, first install the new public leaf fingerprint as a pending pin on **both** API colors while retaining the old active pin. The old+new acceptance overlap starts when the first API color loads the pending pin and lasts at most 30 minutes; do not switch Traefik until both colors report the same rotation generation and accept only those two fingerprints. If preparation cannot finish within 30 minutes, remove the pending pin from both colors and restart the procedure. Then switch Traefik to the new leaf, drain old pooled connections to force fresh backend TLS handshakes, and verify an authenticated handshake to each API color plus the Node leaf-PEM forwarding path. Only after both colors pass, remove the old fingerprint from both APIs and drain any remaining old-cert sessions. Each API checks the peer fingerprint against the currently allowed set for every Node request, including reused connections; an old connection cannot preserve authorization after its fingerprint is retired. Keep backend CA-chain and server-name verification enabled throughout.

Rollback is bounded by the same window. Before switching Traefik, failure rolls back by removing the new pending pin on both colors; the old pin remains active. After switching but before retiring the old pin, switch Traefik back to its old leaf, force fresh handshakes, and verify both API colors before removing the new pin. If verification fails after the overlap expires or after old-pin retirement, stop Node ingress; reinstall the old pin on both API colors, confirm both loaded it, restore Traefik's old leaf with fresh handshakes, and verify before resuming. If the old key is unavailable, issue a replacement under the approved CA procedure and repeat as a new rotation; never bypass fingerprint or TLS verification. API server-certificate rotation similarly deploys the replacement server trust before switching the leaf and removes the old trust only after Traefik verifies both colors.

### Blocking direct-origin access

Source review of [`docker-compose.prod.yml`](../../../../docker-compose.prod.yml) confirms API blue/green services currently publish no host ports, while Traefik publishes web ports. It also shows the APIs and several other services share `automaton-prod`; the existing absence of published API ports blocks public direct-origin access but does not isolate API containers from Docker-network peers. The compose file currently declares no secrets. This is source evidence only, not a live firewall/network probe.

Before Node enrollment, add a dedicated Docker network marked internal and joined only by Traefik and the API colors. Each API color binds its separate Node HTTPS listener only to its address on that network; it has no host port mapping. The dedicated Node SNI route points only to that listener. Ordinary API/tenant hostnames do not route to it. Other containers on `automaton-prod` cannot reach the Node listener because they are not members of the dedicated network; a direct peer that can reach it still fails backend mTLS without a valid Edge-CA Traefik certificate. Keep the bootstrap hostname limited to the one-use enrollment endpoint and route it through the public Traefik edge. Host root/Docker administrators remain trusted and can attach to the network; this design does not defend against them.

## Required identity and lifecycle contract

- A trusted administrator or authenticated BYO account owner authorizes a short-lived, one-use enrollment record before bootstrap. It pins NodeId, InstallationId, owner/scope, allowed profile, control-plane realm and the SHA-256 fingerprint of the approved client public key. The Node locally creates its self-signed client certificate and signed CSR from that key. The bootstrap endpoint verifies the CSR signature and that the certificate carries the same pinned public key, then records the leaf-certificate fingerprint; it does not sign or issue a Node certificate. The token alone cannot choose a key, create a second Node, or widen privileges. The bootstrap host exposes no effect-capable API. A failed or response-lost exchange remains consumed and is recovered against the same pinned installation through an authorized recovery operation.
- The Node client key is persisted in protected installation state, accessible only to the trusted Node service identity (root for the initial privileged Linux service). Certificate subject text is descriptive only. The API authorizes by exact active leaf-certificate fingerprint/revision plus the bound Node API key and current DB/realm/epoch records. Trust-chain validation alone does not grant identity or account access.
- Node certificates are self-signed and pinned per installation, so Node enrollment has no shared issuing root or central Node-CA signing key. The separate service-only Automaton Node Edge CA issues only the Traefik client and API blue/green server certificates. Platform Operations Security Custodians own its offline ECDSA P-256 signing key; two designated custodians control use/recovery and maintain two encrypted offline copies in separate access-controlled locations. The named custodians, media locations, audit procedure and successful recovery drill are pre-enrollment review gates. Do not place the key in the application database/backups, container image, production host or Node installations.
- Node-to-edge TLS uses a dedicated configured Node-management hostname/entrypoint, separate from ordinary tenant and legacy Runner API hostnames. Traefik's SNI-selected TLS option uses `RequireAnyClientCert`: it requires a presented Node certificate but does not validate its chain, because each Node certificate is self-signed. This is required because Traefik selects TLS options during the TLS handshake before HTTP path routing; a path-only router cannot safely turn client-certificate enforcement on for one API route while leaving other routes on the same hostname unauthenticated. Conflicting options can fall back to the default TLS option, which may remove client-certificate enforcement. Traefik strips inbound `X-Forwarded-Tls-Client-Cert` and uses `PassTLSClientCert` to forward the actual peer's leaf PEM. It does not generate or assert a Node fingerprint. The API accepts the forwarded PEM only on the Node listener after backend mTLS authenticates Traefik, parses one bounded leaf certificate, calculates its SHA-256 fingerprint from DER, and verifies validity plus the exact active Node certificate fingerprint/revision and Node-bound API key against current control-plane state. The API origin must not be reachable through an alternate route that bypasses these checks; any direct API route must perform the same Node-certificate pin validation itself. Network reachability, proxy identity, internal TLS and header handling must be proven in deployment tests. Subject names or arbitrary forwarded certificate text never grant access.
- Rotation is a durable prepare/commit operation bound to the current credential revision. The new key proves possession and is bound to the same Node/installation/realm. A pending certificate can call only the rotation completion/status operation; it cannot activate, fetch assignments, submit results or receive effect permits. Commit atomically makes the new fingerprint/revision active and the old one invalid. Retries return the pinned outcome. If the old key is unavailable, recovery requires a separately authorized operator/owner procedure and physical fencing evidence; it cannot self-issue a replacement. Broker credential rotation remains an independent reconciled step.
- Revocation disables the Node binding and advances its credential revision in durable control-plane state. Every Node API request checks the current active binding; a valid CA chain or a still-live TLS connection cannot bypass revocation. Proxy CA trust and API identity mapping must be updated consistently. Revocation prevents new control-plane authority but does not stop already-submitted host effects; N0-B/N0-C fencing and settlement proofs still apply.
- mTLS does not replace realm/recovery-epoch fencing. After database restore, the external recovery register and its current attestation must be checked before API/Worker/route writers or Nodes resume mutations. A new certificate, new random incarnation, larger DB generation, or valid old TLS session cannot stand in for the external epoch.

## Security review observations and disposition

The N0 contracts already make several sound separations: the DB-bound identity supplies authorization; local installation/assignment fences reject stale commands before host mutation; request-intent keys are claimed before allocation; accepted or uncertain effects are never silently rerun; and evidence recovery preserves the original execution tuple. The following ambiguities needed resolution before implementation:

| Review observation | Contract disposition | Remaining gate |
| --- | --- | --- |
| Enrollment pinned a key fingerprint but did not say how the key proves possession or whether a token holder could substitute a key. | Require prior scoped authorization, locally generated self-signed certificate/key, signed CSR, proof-of-possession verification and fingerprint equality before binding. | Review enrollment authority and lost-response recovery; no Node certificate issuer service or shared issuer key is required. |
| TLS termination forwarding could trust a spoofable header or permit a direct-origin bypass; path-only mTLS may not be enforced by a host-wide SNI TLS policy. | Require a dedicated Node-management SNI hostname/entrypoint, strip the supplied header and forward the actual leaf PEM; the API computes and checks the pinned Node fingerprint after authenticating the proxy-to-API channel. Direct API routes enforce the same check. | Verify the actual deployment topology and test all routers/configuration, including conflict/default fallback behavior. |
| Rotation/revocation did not fully constrain the pending certificate or say when the old certificate stops working. | Pending credential is rotation-only; commit atomically switches the exact active fingerprint/revision, invalidating the old binding. API checks current revocation state on each request. | Review operational recovery and deployable proxy/API cache invalidation behavior. |
| External restore-register signing and service Edge CA key recovery are separate security authorities. | Preserve the N0-D external epoch requirement; the Edge CA must not sign restore attestations. The Edge CA signing key stays offline under two-custodian recovery. | Independent review must approve restore-register authenticity/key custody and verify the Edge CA custodians, backup locations, audit procedure and recovery drill. |
| mTLS can be mistaken for authorization or physical process fencing. | State explicitly that certificate proof only authenticates key possession; DB binding authorizes, and local/host-wide effect fences prove ownership/settlement. | Tests and isolated-host evidence remain required before consumers/cutover. |

This is the author's contract review, not the independent security/tenancy/privilege/fencing/accounting review required by N0-D. No external reviewer was engaged. It does not verify that current API endpoints, Runner auth, proxy configuration, certificate issuance or production deployment satisfy these future contracts.

## Required acceptance tests before enrollment or effects

1. **Enrollment binding:** on the separate server-authenticated bootstrap hostname, correct one-use enrollment + matching signed CSR and self-signed certificate binds exactly one Node identity through the bootstrap-only API; wrong key/fingerprint, changed scope, expired/replayed token, invalid CSR proof and competing claims fail without creating another binding. Prove this hostname cannot activate, fetch assignments, submit results or cause host effects and cannot weaken the required-mTLS management hostname. Lost response returns only the original receipt after proof from the same key.
2. **Two-factor and scope:** correct client certificate with missing/wrong Node API key is denied; correct API key without its client certificate is denied at the TLS edge; a certificate/API-key pair from another Node cannot read assignments/artifacts or submit results for this Node. Legacy Runner and tenant auth paths retain their existing behavior.
3. **Proxy and direct route:** Node management uses a dedicated SNI hostname/entrypoint with `RequireAnyClientCert`, isolated from ordinary API routers; test that TLS-option conflicts or default fallback cannot remove the client-certificate requirement. A self-signed Node leaf reaches the API as PEM even though Traefik does not validate its issuing chain. Client-supplied forwarded-certificate headers are stripped and replaced with the actual peer leaf PEM; no proxy fingerprint assertion is trusted. The API computes the leaf fingerprint and accepts only the current DB-pinned Node certificate after authenticating the Traefik backend identity; wrong/untrusted proxy identity is rejected. Direct-origin access cannot bypass these checks; TLS version, server identity and chain failures reject before HTTP authorization.
4. **Node rotation/revocation:** pending Node certificate is limited to rotation completion/status; two concurrent prepare/commit requests are idempotent; response loss returns the committed receipt; the old Node fingerprint is rejected immediately after commit; revoked binding is denied across independent API replicas even with a still-valid certificate and reused connection; unavailable old key follows operator recovery and does not mint a second identity.
5. **Traefik backend leaf-pin rotation and rollback:** both API colors accept exactly the old and pending Traefik leaf fingerprints for at most 30 minutes, and refuse a Traefik switch until both report the same pin generation. After switching, force new handshakes and verify backend mTLS and Node PEM forwarding to each color before retiring the old pin. Inject failure before switch, after switch, beyond the overlap deadline and after attempted old-pin retirement; prove the documented rollback either restores the old leaf/pin on both colors with fresh handshakes or leaves Node ingress stopped. On a reused backend connection, requests authorized under the retired old leaf are rejected; new connections with the active leaf succeed. Never disable TLS verification.
6. **Restore and fencing:** replay a pre-restore certificate, API key, proxy assertion, activation, permit, broker message and result after DB rewind. The old realm/epoch is denied before mutation regardless of certificate validity or larger restored generation; only an attested current external epoch and explicit evidence-import grant can report historical effects.
7. **Authority separation:** changing account/Node ownership still requires N0-C host-wide fencing and outstanding-effect settlement. A valid certificate cannot advance assignment generation, bypass reservations/policy readback, stop arbitrary containers or clear uncertain occupancy.

All tests above are required future coverage; none ran here. N1-A preparation PR #370 was reviewed by the user and merged, but that review was limited to the non-enrolled skeleton and did not review or approve these security contracts.
