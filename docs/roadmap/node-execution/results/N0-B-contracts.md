## Current mechanisms and selected reuse

Source inspected: `src/Automaton.Core/Models/RunnerExecutionCommand.cs`; API services `RunnerExecutionOperationService`, `RunnerExecutionIdentityService`, `RunnerExecutionAdmissionService`, `RunnerExecutionCommandPublisher`, `RunnerExecutionRevocationService`, `RunnerEnrollmentService`, `SelfHostedRunnerInstallationService`, `HostContainerRelayStateResolver` and `HostContainerExecutionOperationService`; Runner `RunnerExecutionJournal`, `RunnerExecutionProcessor`, `RunnerExecutionDeliveryHandler`, `RunnerExecutionQueueConsumer`; infrastructure entities `Runner`, `RunnerHost`, `RunnerEnrollment`, `SelfHostedRunnerEnrollment`, `AppDeploymentTarget`, `DeploymentOperation`, `RunnerExecutionOperation`, `HostContainerExecutionOperation` and `AccountStorageAllocation`.

RM already provides protected durable request/result storage, transactional CAP publication, stable Runner/key authorization, separate execution/management queues, authenticated HTTPS artifacts/results and accepted/result/tombstone journaling. Broker provisioning grants consume-only access to exact execution and management queues. Current Node-equivalent incarnation/generation/policy fields do not exist. The generic operation service accepts an already-completed result without comparing a new result body; Node receipt semantics below require a pinned result digest. Current host-container operations have their own request hash and assignment checks; they are extraction candidates, not a second Node transport.

**One transport:** extend the existing RM execution/management queue + HTTPS assignment/artifact/result path for Node commands. Node never consumes the legacy infrastructure or Hosted deployment queues. Preserve those paths only for explicitly unmigrated executors. No SignalR management fallback, raw host-command queue, or second operation ledger is introduced. SignalR remains only for Studio/presence and the supported BYO tunnel relay.

Types belong with Node enrollment, assignment, operation and journal features; wire DTOs belong in a dedicated Core Node-contract area. Keep existing API operation persistence/publication and admission as owners, extract host effect policy from Runner executors, and do not turn a large Runner service into a general Node utility bucket. The exact project evolution is selected in N0-D/N1-A after deployment compatibility review.

## Request deduplication before workload allocation

There are two hashes and two identities: `ClientIntentHash` binds the normalized authorized client request before allocation; `RequestHash` binds the full immutable executor command after allocation. Comparing the latter cannot deduplicate a client retry because workload IDs, placement, incarnation and resolved defaults may differ. `ClientRequestId` must be supplied/reused by the client across retries; if omitted, reject a create/execute request with 400 `idempotency_key_required`. The server must not generate a new request key for each HTTP attempt. Independently requested reruns use new keys and remain subject to Action retry/idempotency policy.

**Stable key:** `(RequestScopeKind, RequestScopeId, RequestKind, ClientRequestId)`, all non-null. Scope is `account` + authorized account ID for tenant work or `host` + NodeId for administrator host work. RequestKind is the finite use-case kind (e.g. `execute-action` or `deploy-package`), not an internal build/start/probe step. App/target, action key, explicit version/artifact digest, client input/options and explicit client preconditions are in the intent hash, so changing target under the same scoped key conflicts. Actor/access is reauthorized on every replay; original actor remains audited, and knowledge of a key never grants access to its operation/result. No generated operation/workload ID, assigned Node, assignment generation, desired revision, policy snapshot, server deadline or incarnation is in the key or client intent hash.

Persist the key, `IntentSchemaVersion`, normalized protected client-intent bytes/hash and stable root operation ID in the **existing owning durable use-case record**: DeploymentOperation for deployment, AppModuleExecution for an Action invocation, RunnerExecutionOperation for a standalone typed host/file operation. Add a unique index on the stable key in each owner; RequestKind is routed to exactly one owner table, not probed across independent ledgers. These fields are an admission phase of that record, not a new scheduler/quota/dedup service. A provisional root ID used to insert the claim is not allocation of a workload; for an Action whose execution ID later also identifies its workload, only the winning committed root is promoted to that identity. Child commands reference `RootRequestOperationId : Guid` and a deterministic semantic `StepKey : string` (1–128 ASCII characters from a versioned finite step grammar); uniqueness forbids duplicate build/start/dispatch children. A separately authorized recovery successor uses its own recorded step key rather than overwriting an old command.

Ordered admission, shared by every replica:

1. Authenticate, authorize account/App/target and validate the caller's stable request key and basic payload bounds. Read any existing scoped request before generating workload/candidate IDs. For a hit, normalize using that record's pinned IntentSchemaVersion (not today's default serializer); compare exact normalized client intent/hash and return the original root operation/status, or 409 `idempotency_conflict`. Perform no workload allocation, new reservation, artifact publication or new execution/outbox event. A replay can return a terminal original result after its Node incarnation changes; it is not a fresh submission.
2. If absent, enter the existing admission/CAP transaction, take the stable scope admission lock and insert/recheck the unique request-intent claim **before** selecting placement, allocating workload/candidate/desired-revision IDs, or reserving resources. A unique-key loser rolls back its speculative claim and reads the winning committed record in a fresh transaction/context. If the winner rolled back, it may compete anew. No loser allocates anything. No process-memory cache or preliminary unlocked lookup is the concurrency authority.
3. Only the winner resolves policy/placement/immutable artifact version and allocates workload/revision/reservation/command IDs. Pin normalized resolved defaults separately from the client intent; a retry of omitted defaults returns that first resolution even after policy/config changes. A client-supplied expected revision remains part of intent and is validated for the first admission; a matching duplicate returns the original outcome rather than applying it against a newer revision.
4. Commit the claimed root, workload/reservation, immutable child command and CAP outbox intent atomically. Crash before commit rolls everything back; crash after commit/before HTTP response returns the same root on retry. Rejected admission may be persisted as the root's Failed/no-effect outcome with no reservation/outbox, so a repeated key returns that rejection; a deliberate new attempt after capacity restoration uses a new key. Neither cancellation, expiry, recovery nor incarnation change clears a committed request key.

If request intake needs a resumable upload phase, commit only an `IntakePending` root/claim before staging bytes, with no workload or reservation. Matching retries resume that root's bounded upload; different bytes/digest conflict. Finalize admission under the same locks/key and transaction above after length/hash verification. Cleanup can expire its artifacts, but must retain its key/hash and terminal expiry outcome; it cannot turn an old key into new work. Existing already-staged immutable artifacts may be referenced without extra staging on duplicate. Root/command admission in the same RunnerExecutionOperation store uses distinct record roles (`request-intent`, `command`) so an incomplete intake root can never be dispatched as an executable Node command.

**Concrete retry/race example (symbolic IDs):** account A submits `execute-action`, key K, App P/target T, Action `send-report`, input `{"reportId":"weekly-42"}`. API replica 1 claims `(account,A,execute-action,K)`, then allocates root R, workload W, reservation Q and child C at Node incarnation 4. Replica 2 concurrently submits the same intent and key. It returns R and C's existing status; it cannot allocate W2/Q2/C2 even if it observes a newer placement or defaults. Both responses identify the same execution. Changing input to `weekly-43` under K returns 409 before any allocation. A new key K2 intentionally creates a separately admitted execution. If replica 1 dies before its transaction commits, W/Q/C/outbox and its claim do not survive; the eventual winner performs one committed allocation. If it dies after commit, retry K finds R without another event or reservation.

## Enrollment, session binding, rotation and revocation

**Security decision S-B1 — proposed, not approved:** mTLS/client certificates are a candidate way to bind Node credentials to client-key possession. Certificate issuance/trust bootstrap, key storage, renewal/rotation/revocation, proxy identity forwarding and operator recovery add work not present in RM today. The certificate-specific fields, ECDSA choice, guarantees and tests in this section are conditional on independent security/operational review selecting this proposal; they are not authorization or an already-approved implementation requirement. That review must select mTLS or a specified alternative satisfying the replay/threat boundary before authentication consumers are implemented. Do not silently downgrade to bearer-only authentication or claim bearer-replay resistance while the mechanism is unresolved.

Threat boundary: control plane and host administrator/root are trusted; tenants cannot read management configuration, client private keys, broker credentials or Docker socket. A hostile host root can forge observations or copy all identity material; this proposal does not provide hardware attestation. Such a host cannot be represented as secure managed hostile multitenancy. Merely replaying a bearer credential must not create a second executor.

1. Authorized administrator issues managed enrollment; an authenticated BYO account owner may enroll a host scoped only to that account. Binding to a managed host/shared accounts requires administrator authority. Enrollment pins Node/installation/profile and client certificate public-key fingerprint in a short-lived one-use record. Installer generates the private key locally; approval binds the fingerprint before privileged activation. A token alone never changes an existing Node binding or expands scope.
2. **If S-B1 is approved**, extend the same HTTPS path with mutual TLS client proof for Node endpoints, in addition to the existing bound API key. Use a client certificate with an ECDSA P-256 key, persisted root-only, validated against configured issuing trust and the exact active fingerprint/revision in DB; no certificate subject name grants authority. Tenant endpoints and legacy Runner auth are unchanged. If TLS terminates at the edge, only a configured authenticated proxy may forward verified client identity, and incoming client-supplied certificate headers must be stripped. If selected, this trust forwarding requires implementation/deployment tests; it is not a current feature. No owner-key fallback for Node endpoints.
3. Node acquires one OS-held installation-wide exclusive file lock before activating or opening effect workers. Lock path is in configured protected state, fixed by installation, not supplied per request. It holds that same inode until all effect workers end; never unlink/recreate it for takeover. A second local process fails startup. Acquire per-assignment mutation serialization inside that lifetime lock.
4. Activation request contains `NodeId`, `InstallationId`, `ExpectedIncarnation`, `ActivationRequestId : Guid`, `CertificateRevision : long`, supported schema versions and capabilities. API verifies bound key + certificate, scope and CAS, allocates `Incarnation + 1`, and stores an activation receipt. Same request ID/body returns that receipt; reuse with different body is 409. New activation cannot displace an active incarnation merely because its heartbeat is old. Initial enrollment has no prior executor; normal restart must prove the prior management process/effect workers ended under the installation lock, then enter recovery-only activation to reconcile surviving workloads and journal records as specified below. A surviving OCI workload is not a second manager, and need not be killed merely to observe it. Cross-host replacement requires explicit operator fencing evidence and cannot auto-activate from copied config. N0-C defines the cutover proof record; until then replacement remains fenced.
5. API returns the current incarnation and exact admitted profile/policy bindings. Node fsyncs activation/local assignment records before acknowledging readiness. Missing/corrupt state disables mutations and requires inventory/recovery, never generation zero. On startup Node does not automatically execute queued bodies from its disk journal without current authenticated assignment authorization.
6. Credential rotation is an authorized durable operation with expected credential revision, verified new key/certificate possession and bounded prepare/commit phases. Pending certificate has rotation-completion access only; only the committed certificate/key can obtain effect authorizations. Rotate broker consume credentials separately with observable reconciliation. Rotation preserves Node/assignment IDs, cannot expand account scope, and does not transfer execution ownership. Lost credential delivery is retried through pinned enrollment/rotation identity; do not mint another active identity silently.
7. Revocation transaction disables Node admission, advances credential revision and fences its control-plane binding; API denies new assignment/artifact/activation/result writes from revoked credentials immediately after commit. Broker revoke/disconnect is a tracked external cleanup step. Previously accepted host work may still run: remote revocation is **not** physical fencing. Persist uncertain operations/occupancy and require verified stop before transfer. Operator-supported recovery can import a saved old journal result as evidence under a fresh authorized recovery operation; revoked keys cannot resurrect themselves to report it.

Two legitimate Nodes have different DB/certificate/key/queue bindings. Node B cannot use Node A's operation/result identities with B's credentials; under the proposed S-B1 mechanism, an A bearer key replay without A's client key would fail TLS proof; that protection remains conditional on review and implementation. Replaying A's valid result cannot change B's assignment or current A generation. Full cloning of A's private key and disk state by trusted-root compromise is outside this guarantee; the API must not permit an automatic second activation, and a privileged stolen active credential must be revoked and the host fenced. Do not claim cryptography alone proves a physical process has stopped.

Node-specific authorization derives allowed accounts/host-management rights from the durable enrollment binding, not `Runner.Purpose` or legacy owner-key authorization. BYO ownership authorizes only that host's assigned account, not managed host approval, another account or unrestricted host execution. An Infrastructure-purpose transport row alone cannot call legacy provisioning/workflow endpoints as a Node: those endpoints must reject a Node-bound principal, and new Node handlers enforce the finite surface here. Enrollment exchange response loss leaves a used token used; recover the same pinned installation through authenticated client-key proof and an enrollment recovery operation, or explicitly fence/replace it. Do not reuse the token to create a second principal. Certificate trust/issuance and proxy configuration are proposed S-B1 work, conditional on its approval, not assumed existing infrastructure.

## Local fencing and operation authorization

Database generation, credential expiry and broker removal cannot stop a partitioned old manager. The initial same-host migration must stop/drain old Infrastructure/Hosted execution paths, disable their restart sources, revoke their credentials/queues and verify no submitted host effects remain before recording Node ownership. Remote host transfer with unavailable stop evidence is blocked. Existing workloads may keep serving if safely adopted; no second manager is admitted over the same resources.

For every ordinary mutation (recovery-only evidence import/receipt reads use the explicit grants below) Node holds the installation lock and assignment effect gate, obtains a fresh authenticated HTTPS assignment immediately before the effect, compares Node/incarnation/account/assignment/generation/policy/workload/revision/request digest with its fsynced local fence, and inspects owned resource labels/storage identity. Recheck before each subsequent host effect in a multi-step operation. The API serializes permit issuance with ownership-change state. Entering `Quiescing` prevents new permits; ownership never advances while an issued permit/effect is unsettled. The HTTP request/operation ID is the permit identity; there is no transferable bearer execution token or signed offline lease.

After a durable local acceptance record, Node reports acceptance before its first effect; crash/lost acceptance acknowledgement is treated as potentially accepted. API issuance itself already keeps the operation/reservation outstanding, so a crash before acceptance cannot make transfer safe by timeout. No new mutations during API outage, unknown policy, missing lock, fence mismatch or failed inventory. Running workloads continue under their already-applied policy; authorized in-flight effects can finish and journal results. Cancellation/timeout can stop only the exact already-authorized child workload under its recorded fence; it cannot promote, retarget, delete persistent data or adopt a newer generation while disconnected.

Policy and desired-workload advancement are explicit CAS transitions, not ordinary fence-matching requests: ApplyAccountPolicy carries expected **old applied** revision/hash and proposed new snapshot; it records pending policy before effect and records applied revision only after readback. Other commands remain blocked on unverified pending policy. A new workload intent carries expected prior desired revision (null only for first creation) and new desired revision; validate the current authoritative assignment, durably record intent under the effect gate, then execute. A stale request cannot advance either value simply by containing a larger number. These transitions preserve Node/incarnation/assignment generation; only the fenced ownership-change protocol changes owner fields. Failed/uncertain application retains old effective reservation plus pending debt, never claims the new policy is enforced.

Local fence advances only through an authenticated ownership-change operation after old workers/permits have settled and the new tuple is written atomically. A rollback creates another increasing generation; never restore an old counter. Engine operations already accepted by Docker may outlive the caller: reconcile completion and verify absence of writers before fence transfer. Timeouts/lease expiry alone are never stop proof. N0-C specifies that proof and local storage/cgroup adoption, not a new distributed lock service.

The host itself also has one management owner: a legacy privileged Infrastructure Runner must not remain capable of host mutations on an adopted Node host just because its remaining accounts differ. Retain incompatible legacy cohorts on hosts that have not transferred host authority, or block that host's cutover until all overlapping host-management paths are fenced. N0-C must account for the entire host boundary when planning account-by-account migration. Multiple local lock files in different installation directories are not a solution; replacement must fence the previous installation and bind the configured host-level lock/state location.

## Proposed version 1 wire contract

These are new DTO specifications extending RM, not current API routes/models. Use strict camelCase JSON, UTF-8, GUID `D` strings, UTC `DateTimeOffset` strings and ordinal operation enums. Revisions/incarnation/generation are positive signed Int64 represented as **decimal strings** on the wire to preserve values in JavaScript; zero, leading sign, overflow, missing or null are rejected. Unknown version/kind/fields, duplicate JSON properties, nonfinite numbers and additional payload arms are rejected before acceptance. Server emits a deterministic DTO byte representation; request digest is SHA-256 over these exact persisted canonical request bytes, not tenant JSON reserialization. Store those bytes protected and deliver the same bytes in base64 with their digest; Node hashes decoded bytes before strict parsing. Result bytes use the same pin-and-replay rule. Do not hash Data Protection ciphertext or secrets into public IDs.

Broker notification (identity only, no paths, scripts, limits or secrets):

```json
{"schemaVersion":1,"controlPlaneRealmId":"40000000-0000-0000-0000-000000000001","recoveryEpoch":"2","operationId":"10000000-0000-0000-0000-000000000001","runnerId":"20000000-0000-0000-0000-000000000001","nodeId":"30000000-0000-0000-0000-000000000001","incarnation":"4"}
```

`runnerId` is the Node TransportRunnerId, retaining current queue naming/routing. Extend the existing dispatch event/command with versioned Node identity; broker notifications only wake HTTPS assignment. Queue order is not ownership authority. Notification incarnation mismatch is discarded/reported without effect, never adopted into local state. Management uses its separate bounded consumer for cancellation, reads, reconciliation and tunnel reconnect; concurrency comes from validated configuration and account admission, not a second per-Node entitlement limit.

Initial bounds: reuse `RunnerFileTransferBounds.MaximumBytes` (200 MiB) and configured shared package-store capacity; v1 control/request and terminal-result decoded bodies are at most 1 MiB each, broker notification at most 4 KiB, inline diagnostic tail at most 64 KiB. Larger logs/results use authorized artifacts subject to existing Action/file bounds, not broker payloads. Validate before allocation where possible. UTF-8 length/hash fixed on admission; GUIDs and hashes never truncated. SHA-256 is 64 lowercase hex; OCI references require registry/name plus `@sha256:` and 64 hex digest. Reject missing required artifact metadata, duplicate volume IDs or payload mismatch with 400/413; artifact corruption yields terminal `Failed/artifact_mismatch` before any effect.

Assignment response: `schemaVersion`, operation/Node/incarnation and request hash, `disposition` (`execute`, `cancel`, `already-applied`, `obsolete`, `blocked`), optional `requestBase64`, optional bounded reason code and optional terminal receipt. Only `execute` includes complete request bytes. `cancel` carries the pinned target operation/fence, not new tenant code. `already-applied` includes accepted result digest; `obsolete` has no executable body. `blocked` is retryable with configured backoff and never authorizes effects. An operation requiring policy advancement first receives a separate typed ApplyAccountPolicy operation; no lazy policy override inside another request.

Terminal result: required schema version, operation ID, exact immutable identity tuple (including account/assignment/generation where applicable), request hash, `outcome` (`Succeeded`, `Failed`, `Cancelled`, `Lost`), `errorCode : string?`, start/finish UTC timestamps, effect classification (`none`, `confirmed`, `uncertain`), bounded diagnostics and a typed result matching operation kind. No success for a required but missing readback/probe/result artifact. Lost requires uncertain effect; cancellation after acceptance may be uncertain. Observed container IDs, digest, applied policy and artifacts are evidence, not new target authorization. Node saves exact result bytes/digest before submission.

Receipt: `accepted` or `already-applied` with operation ID and pinned result digest; different result digest is 409 `result_conflict`, never silent success. Old-generation results can be archived as `historical` evidence through the explicit current-session recovery grant, with original executor and reporting incarnation recorded separately; they cannot complete the new desired revision, release another generation's reservation, change routing or claim ownership. A historical receipt must identify the recorded digest before local payload cleanup. Revoked credentials receive 401/403; ordinary stale-incarnation callbacks are rejected. Supported current-session recovery import/receipt reads below do not require the retired credential to remain valid. Foreign account/Node operation lookup returns 404 (no disclosure); bad authentication 401, authenticated but prohibited command 403, stale incarnation/generation/policy/revision or mixed selector 409, unknown version/capability 422, unavailable authority 503. Explicit terminal rejections use `Failed` with typed code, not success or indefinite retry.

## Support decisions for Node cohorts

These decisions are proposed support scope for the migration, not removals from current production.

- **BYO Standard web/static/Actions/files remain supported.** BYO host has its own Node/RunnerHost and account allowlist; targets select Node assignment. Files keep existing transfer/media/session semantics and authorization. No legacy owner API key authenticates Node management. No direct tenant access to Node endpoint or filesystem follows from owning an app.
- **BYO runtime tunnels remain supported through N4.** Node hosts the existing fixed-destination runtime gateway/SignalR tunnel adapter addressed by TransportRunnerId, bound to active Node incarnation and API instance. Gateway resolves App/target → current Node workload; public/private/auth policy stays in the API. Existing bounded reconnect/latest-target ordering and instance-local routing remain, including possible interruption/503. No cross-instance relay, arbitrary TCP forwarding or SignalR command fallback. The tunnel adapter must not register retired execution handlers. N3-D/N4 must test files and tunnel parity before declaring the cohort migrated.
- **Workflows and custom steps are retained only in a named temporary legacy scope, not accepted Node payloads in v1.** API workflow requests targeting Node return 422 `node_workflow_unsupported`; no hidden selection of old Runner. Existing accounts with active workflow/step dependencies remain unmigrated on their explicitly assigned legacy executor, with unchanged permission checks. Owner: workflow/runtime migration maintainers; removal condition: isolated OCI workflow/step contract plus parity/cancel/uncertain-effect tests, or explicit product retirement and zero retained dependencies. Revisit in N0-D/N3-A; no unplanned interpreter/framework is included. Full N4 retirement is blocked while supported dependencies remain in this scope.

Owner: runtime/security maintainers; removal condition: separately reviewed capability-isolated equivalent or explicit support retirement and migration of every reference. Operator diagnostics requiring arbitrary host access stay manual host administration outside tenant APIs; Node installation/update/repair remains the operator-controlled N1-D workflow.

## Recovery across Node incarnation changes

An incarnation change invalidates old **execution permits**, not durable request keys, workload identity, reservations, accepted markers or terminal evidence. Original command C remains immutable with its original Node/incarnation/assignment/generation/request hash. The restarted Node must never rewrite C from incarnation 4 to 5, recompute its request hash, clear its accepted marker, or call its body under incarnation 5. Client retry still resolves to its original root R before allocation.

**Recovery-only activation:** after verified prior manager shutdown and installation-lock acquisition, activation CAS creates incarnation 5 with `NodeManagement.Status = Recovering` (add this status to the proposed model). Preserve a local recovery checkpoint containing previous/current incarnation, activation request ID, unresolved command IDs and journal inventory digest before acknowledging activation. Account mutation admission remains paused; fresh workload execution is disabled. API authorizes read-only inventory, evidence import and receipt retrieval in this mode, authenticated as the new active incarnation. If observation establishes that a surviving resource must be stopped, a separate control-plane-authorized recovery StopWorkload/CancelOperation may target that exact original resource after old-manager/permit fencing; no create, promotion, Action execution or arbitrary cleanup is allowed. API/control-plane and local recovery checkpoint persist before normal Active readiness. An activation retry returns the same incarnation/receipt; another crash starts a further epoch and resumes the checkpoint without clearing old evidence. Bootstrap recovery entry points are versioned RM/HTTPS management operations restricted to this mode, not a fallback transport or tenant recovery endpoint.

Recovery-only activation does not claim issued host effects are settled: old OCI workloads or asynchronous Docker effects may survive. Inspect them read-only with exact durable ownership/resource identities. If prior process death/restart prevention is not established, do not activate a competing manager; if state is corrupt/missing or host differs, remain blocked for operator recovery. Incarnation advancement on the same installation alone does not advance assignment generation. Transfer of account/host ownership still requires the separate fenced protocol; it cannot be smuggled through restart recovery.

**Explicit evidence-import contract:** add management kind `ImportOperationEvidence` and read-only `ReadOperationReceipt`, usable only by the active Node recovery session or a separately authorized operator recovery principal. Import fields are `RecoveryOperationId : Guid`, `OriginalOperationId : Guid`, `OriginalNodeId : Guid`, `OriginalIncarnation : long`, `OriginalAssignmentId : Guid?`, `OriginalGeneration : long?`, `OriginalWorkloadId : Guid?`, `OriginalDesiredRevision : long?`, `OriginalRequestHash : sha256`, `ReportingIncarnation : long`, `EvidenceKind : enum` (`saved-terminal`, `observed-outcome`, `uncertain`), original exact terminal bytes/hash when present, and authorized observation/artifact references. ReportingIncarnation must equal current authenticated incarnation; the original tuple/hash must equal persisted C. RecoveryOperationId is a durable control-plane grant bound to this original command, current reporting session and allowed evidence kind; it cannot be chosen freely by a tenant or another Node. Persist recovery authority in the existing operation store as a non-tenant recovery operation, not a separate result/transport ledger; unique `(OriginalOperationId, ReportingIncarnation, RecoveryPurpose)` makes grant retry idempotent. Record importer separately from original executor. Node saves a distinct recovery-import journal record; it must not modify original terminal bytes to insert the reporting epoch.

API checks original result/effect/claim and artifact consistency, then CAS-pins a terminal result only if C has no terminal result. A saved terminal result from incarnation 4 can complete **that original C and its still-current root/workload revision** through incarnation 5's recovery import, without calling it a new execution. Existing identical digest returns already-applied; a different digest is 409 `result_conflict`. If C is already terminal Lost/cancelled by reconciliation or its assignment/workload revision was superseded, retain new evidence as historical only; never overwrite the terminal result or project it onto a new generation/revision. Receipt identifies OriginalOperationId, original request/result digest (or historical evidence digest), RecoveryOperationId and ReportingIncarnation. ReadOperationReceipt allows the current authorized recovery session to retrieve that original receipt even when the old credential/incarnation can no longer submit. Foreign/revoked sessions are denied. Persist receipt locally before clearing private evidence or acknowledging obsolete broker delivery. Same import/receipt request after a response loss returns the pinned outcome without new effects.

| Original C at restart | Permitted recovery under new incarnation |
| --- | --- |
| Queued and **provably never issued** | Transactionally fence C as Failed/`superseded_incarnation` and CAS-link one successor C2 at current incarnation, same root/workload/reservation and unchanged intent; publish C2 in that transaction. Execution deadline/auth/policy must still pass; otherwise fail/cancel original root without execution. Root remains pending while C2 is active; C's supersession is not user-visible root failure. Old C is never executable. A unique nullable `RecoverySuccessorOfOperationId` on C2 plus the root/StepKey constraint and current-child CAS prevent multiple replacements; each later safe restart supersedes only its then-current never-issued child, preserving the chain. |
| Issued/accepted/executing, no terminal | No automatic ExecuteAction/body successor, even if local accepted marker is absent. Read-only inspect exact owned resource; import confirmed outcome or Lost/uncertain evidence. If a job still runs, record occupancy and keep reconciliation-only until outcome/required stop is established. Separate cleanup/cancel authorization, if needed, must be scoped to that resource and may be admitted only after the original permit is fenced and manager-stop proof holds; it cannot re-execute the original body. |
| Saved terminal, API not terminal | Import exact saved bytes through the current reporting incarnation and preserve original executor identity/hash. One result projection; no workload allocation, new reservation or body call. |
| API terminal, local receipt missing | Read receipt/compare saved digest; identical evidence is already-applied. If only historical evidence is accepted, retain the original terminal outcome and record that distinction. No second execution. |
| Missing/corrupt journal or uncertain resource ownership | Do not infer never-executed from absence. Keep RecoveryRequired/occupancy debt; source a durable outcome from verified resources or report Lost. Unknown resources are not removed to make recovery pass. |

**Activation/recovery completion:** API CAS and Node fsynced checkpoint record each original permit as fenced, with result/uncertainty and its resource occupancy disposition. Node enters Active only after unresolved old management permits for the affected assignment have no path to mutate, its fence/policy are reconciled and occupied resources are accurately reserved. An observed legitimate running OCI workload may remain running under its original identity and be monitored/adopted without re-execution once its management permit is settled; a required resource stop uses the narrow current-session recovery command above, so recovery does not wait for an old manager callback that can never succeed. A Lost logical execution may retain cleanup debt/occupied capacity; this is not a free reservation. Re-admission of an unaffected assignment requires an explicit per-assignment ready record, not a global heartbeat shortcut. Recovery cannot deadlock by requiring the old incarnation to send its final callback: the new recovery grant explicitly authorizes evidence import/receipt reads, but never old-body execution. Any further effect (including cleanup) is a new current-incarnation typed command with explicit scope and fresh authorization. Recorded child resource ID/labels remain those of their creation; observation under a newer session does not relabel evidence as a new execution.

**Concrete saved-result example (symbolic IDs):** root R/request key K allocated workload W/reservation Q/command C on Node N, incarnation 4, assignment A generation 7. C accepted and ran once; its local terminal bytes B/hash H were saved but the API callback failed. After manager 4 is proven stopped, session 5 activates Recovering. Recovery grant G permits `(C,N,4,A,7,RequestHash(C))` evidence import by reporter 5. It submits B/H unchanged, records API's receipt, and C becomes Succeeded with original executor incarnation 4 and importer 5. A lost import response replays B/H and returns the same receipt. R, W, Q and request key K are unchanged. If C had no terminal evidence after an accepted Action, recovery records Lost or observes its original running job; it does not issue a new ExecuteAction. If C had never been issued, it may instead have exactly one fenced successor C2 at incarnation 5 using W/Q, with C explicitly non-executable. A result later presented by incarnation 4 cannot authorize effects or overwrite C2; historical evidence is recorded through authorized recovery only.

## Journal v1 and crash/acknowledgement transitions

Reuse RM's operation lock, accept-before-effect, saved-result replay and retained cancellation/acceptance tombstones, adding Node identity/fence/digest/version records. Store under configured root-only management state on the supported durable local filesystem, outside tenant quota, public output and OCI mounts. An entry contains schema version, exact request bytes/hash and identity tuple, issued/accepted phase, observed resource references, exact terminal bytes/hash and API receipt. Local inventory labels must match durable ownership; labels alone are insufficient.

Use same-directory temporary writes, complete serialization, file flush/fsync, atomic rename and directory fsync for activation, fence, phase/result and receipt updates. Existing `RunnerExecutionJournal.SaveAsync` flushes the file then moves it, but does not implement versioned Node fences or explicit directory fsync; extraction requires those additions and power-loss testing. Failure to durably accept means no effect; failure after an effect retains uncertainty and never runs the body again. Hold the installation and per-operation/assignment locks through host effects and journal updates; management cancellation records intent without needing the gate held by the body. Never unlink lock inodes or garbage-collect a record still referenced by active ownership/workload state.

| Durable phase / boundary | Next transition and restart behavior |
| --- | --- |
| API operation + CAP committed, no local entry | Redelivery obtains current assignment. Queue receipt never authorizes execution by itself. Reservation remains outstanding. |
| Fresh permit issued; local validated, not accepted | Revalidate every fence/digest under gate; durable accept before effect. Crash cannot prove no acceptance remotely; reconciliation settles issued permit before transfer. |
| Accepted, acceptance callback missing | Replay acceptance, never create another operation. No first effect until API confirms acceptance and current fence. Crash remains potentially uncertain even if effect was unlikely. |
| Accepted/executing, no terminal after restart | Use recovery-only activation and explicit new-session recovery grant; inspect exact owned workload/attempt: recover confirmed container/job outcome or report Lost. Never rerun uncertain Action/external effect. A new explicit Action request follows its retry/idempotency policy, not queue redelivery. |
| Effect done, result write failed | Keep permit/reservation unresolved; no body retry. Reconcile owned resources or Lost. In-process cached result may retry persistence but is not durable proof after process loss. |
| Terminal saved, HTTPS unavailable/lost receipt | Same incarnation resubmits identical bytes/hash with backoff; changed incarnation uses ImportOperationEvidence preserving original tuple. Identical API result returns same digest; conflicting result is observable conflict requiring recovery. Broker remains unacknowledged until terminal/historical receipt is durable locally. |
| API terminal committed, broker ack lost | Same-incarnation redelivery fetches already-applied receipt; a new incarnation uses authorized ReadOperationReceipt; validate digest and persist acknowledgement, skip body. Never use current assignment to reinterpret old result. |
| Cancellation before acceptance | Persist cancellation tombstone, return Cancelled/no effect; late queued body is refused after cleanup/restart. |
| Cancellation/timeout after effect starts | Record intent, stop exact workload where supported, observe termination; report Cancelled/Failed with effect uncertainty or Lost when outcome cannot be established. Do not release occupied resources until confirmed. |
| Revoked/stale generation or unknown journal version | No new mutation; quarantine entry and retain diagnostic/cleanup debt. Supported recovery imports evidence and explicitly settles original reservation. No permissive decoder fallback. |
| Terminal acknowledged and retention elapses | Private request/results/logs can expire under configured policy; retain compact acceptance/cancellation identity and request/result digests until an authenticated operation-retirement watermark proves replay inadmissible. Without that watermark keep tombstones. Disk pressure rejects new work, never deletes active journal evidence to continue. |

API states are proposed extension of the existing operation row: `Queued → Issued → Accepted → Executing → Succeeded/Failed/Cancelled/Lost`; `CancellationRequested` and `RecoveryRequired` are durable flags, not success states. Acceptance/phase callbacks are idempotent CAS on the pinned tuple; a saved terminal can arrive without an observed Executing callback. Issued/accepted ambiguity is Lost/recovery, never automatic return to Queued. Completion of the execution does not itself imply desired deployment/publish success: existing finalization/probes and policy readback still own those projections. Resource release uses confirmed termination/cleanup under the original reservation identity; a Lost Action can finish its logical execution while retaining physical occupancy debt.
