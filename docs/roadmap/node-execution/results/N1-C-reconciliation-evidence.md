## Proposed v1 model contract

These records are bounded data-transfer objects, never capabilities or classifications. A snapshot contains at most 4,096 observations; each observation records a label count from 0 through 64, and all externally variable identifier fields have explicit length/format limits. No raw label value, physical ID, host path, tenant file content or arbitrary state string is carried. Exceeding a collection/value bound is rejected by the DTO validator. A future collector must represent an incomplete/failed/bounded listing with `Completeness=Incomplete` and a closed reason; it must not truncate and call the remainder complete. This DTO has no wire serializer or promised encoded-byte limit; any future transport codec must define canonical bytes and its body bound before use. Identifiers are nonempty GUIDs; positive revisions/generations/epochs are lossless decimal strings; digests are lowercase SHA-256. Times are UTC and are not proof of freshness by themselves.

`NodeInventorySnapshotV1` contains `schemaVersion`, `controlPlaneRealmId`, `recoveryEpoch`, `nodeId`, `installationId`, `incarnation`, `hostBootIdSha256`, `engineIdentitySha256`, `snapshotId`, `observedAtUtc`, `observationSource`, `completeness`, optional `incompleteReason`, `observations[]`, and `snapshotSha256`. `observationSource` is one of `DockerEngine`, `CgroupV2`, `StorageProbe`, or `TestFixture`. Completeness is exactly `Complete` or `Incomplete`; a complete snapshot has no incomplete reason, and an incomplete snapshot has one of `SourceUnavailable`, `PartialEnumeration`, `SourceChangedDuringRead`, `BoundsExceeded`, or `CollectionFailed`. Invalid input is rejected; a future collector must convert a failed/over-bound acquisition into an explicit incomplete result rather than an empty host. All boot/engine/snapshot digests are opaque lowercase SHA-256 values: without a codec/preimage they are shape-checked only and prove no identity or freshness. The DTO contains no credentials, certificate material, tenant content, raw paths, physical identifiers or raw logs.

Each `NodeResourceObservationV1` contains `resourceKind` (`Container`, `Volume`, `Cgroup`, or `StorageDomain`), `physicalIdSha256`, closed `observedState` (`Present`, `Running`, `Stopped`, `Unknown`), `labelCount`, `labelSetSha256`, and `physicalIdentitySha256`. Raw labels and physical IDs remain inside a future permissioned local provider and do not cross this model boundary. Digest fields are opaque shape-checked values, not proof of physical adoption. No mount/device/inode/cgroup path evidence is represented here.

`NodeResourceOwnerBindingV1` is a data-only representation of a future durable-authority row: realm, recovery epoch, NodeId, InstallationId, account ID when account-scoped, assignment ID and positive generation, effective policy revision/digest, owner kind/ID, resource ID/kind, and owner-record revision. Host-level Node resources have an explicit host owner scope and cannot smuggle an account owner. Workload owners additionally require workload/revision and the stable operation/reservation identity from N0-B/N0-C; partial or mixed scopes are invalid. This DTO does not create or persist such a record.

This preparation does **not** define or implement `NodeResourceAssessmentV1`, a label namespace, label-to-owner mapping, physical-identity digest preimage, or any classification function. In particular, `MissingOwned`, `OrphanCandidate`, `Foreign`, `Conflict` and `VerifiedMatch` are deferred until N1-C consumer design fixes an exhaustive stable resource scope, versioned label keys and their exact mapping to the current binding, plus the unique durable ownership-row key. A future `MissingOwned` result requires a successful complete enumeration of that exact resource scope with stable engine/boot identity and consistent pagination; partial, raced or disappearing inventory is `Incomplete`/`Unknown`, never absence. Any future classification is diagnostic only and cannot settle an uncertain effect, clear cleanup debt, release occupancy or authorize repair/adoption/deletion. N0-C's richer mount/filesystem/cgroup/writer proof remains a separate physical-adoption gate; identity correlation alone is insufficient.

No field in these v1 data models represents an action, permission, grant or assessment. Old incarnation/epoch observations remain historical data with their original tuple and cannot be relabeled to the current binding. Cross-incarnation evidence import is separately gated by the reviewed N0-B grant protocol and stateful N1-B/N1-C consumers.

## Ownership and recovery boundaries

The future API durable ownership record and current external recovery register are authoritative. Docker/cgroup/filesystem labels are corroborating evidence only. A Node service must hold the installation lock, freshly verify the external realm/epoch, authenticate its binding, and revalidate the complete assignment/generation/policy tuple immediately before any eventual effect. Local high-water state, a signed but cached restore file, labels, names, an expired lease, or database incarnation alone cannot authorize adoption or deletion. If the register, ownership record, engine identity, lock or assignment is unavailable, produce `Incomplete`/`Unknown`, remain `RecoveryRequired`, and do not mutate.

Inventory read crashes are idempotent and have no external effect. A partial list, disappearing resource, engine restart, boot-ID change, or snapshot over a bound is an incomplete observation, not evidence of absence. A later snapshot gets a new `snapshotId`; it does not overwrite prior durable effect evidence. No cleanup debt is created by this pure model because no owner record/cleanup transaction exists here. Future cleanup must retain reservation/occupancy until exact owned effects are settled and referenced persistent data is proven safe to retain.

## Named preparation tests and later acceptance

Pure data-model tests for this preparation: `InventoryTupleRequiresRealmEpochAndInstallation`; `HostAndAccountOwnerScopesAreDisjoint`; `OwnerBindingRequiresCompleteScopedFields`; `IncompleteSnapshotRequiresClosedReason`; `SnapshotAndObservationCountsAreBounded`; `LabelCountAndAllDigestShapesAreBounded`; `ClosedEnumsRejectUnknownValues`; `CollectionsAreDefensivelyCopied`; `PortableModelContainsNoRawLabelsPathsOrCredentials`; and `ModelsExposeNoAssessmentOrAction`. Classification cases are deliberately deferred with the classifier contract. When that contract is reviewed, it must include labels-only/no-owner, incomplete snapshot, conflicting duplicate claims, wrong realm/Node/account/generation, identity mismatch, stale incarnation/epoch, and a complete stable snapshot that proves an owned resource absent; only the final case can report diagnostic absence, and none can settle effects or release capacity.

Those tests prove only value validation, not real host ownership. Before any future inventory consumer or effect, required isolated acceptance remains: actual disposable Docker inventory with forged/incomplete labels and foreign resources untouched; restart after create-before-callback discovers the exact owned resource without duplicate allocation; stale assignment/realm/epoch/current-register proof blocks effects; cgroup v2 and storage identity are read back from the host; disconnected API defers uncertain management; repeated cleanup retains referenced data; and interrupted cleanup converges without releasing occupied capacity. MySQL ownership-record races require independent contexts and the actual migration. Linux cgroup/storage checks require a disposable host fixture with the kernel facilities under test; mocks do not establish those guarantees. None is performed by this preparation.

## Decisions and gates

This contract does not choose a concrete Docker label namespace, Node owner-row schema/migration, cgroup inventory implementation, storage path/permission exposure, engine API dependency, mutation ordering or cleanup policy. Those must be resolved against N0-B/C and reviewed before their consumers. A material unknown blocks only the affected consumer; it does not block the pure model or N1-D's independent diagnostic-format preparation. Actual B1 security/tenancy/fencing/accounting approval remains necessary before adding any inventory/effect consumer. B1, the N1-A PR #379 review/merge, operational HFA/register custody, deployed listener evidence and live inventory remain separate gates. No production changes or live access were made.
