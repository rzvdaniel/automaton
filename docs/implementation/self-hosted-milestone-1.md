# Self-hosted milestone 1 implementation guide

This guide preserves the original M1 source baseline, implementation sequence and deferred acceptance cases. M1 implementation is merged; the sequence below is reference material, not a fresh task list. The [self-hosted roadmap](../roadmap/README.md) controls current scope and ordering.

Updated priority (21 October 2026): demonstrate one management Runner installation and the CLI create/assign/deploy/open/update flow, then remove legacy paths in M4 for a fresh-install target. Do not restart the completed M1 preparation sequence or implement extra capacity/storage features from this older inventory. Second-machine acceptance, additional monitoring/cleanup automation, Runner self-update, backup automation and feature expansion are deferred until after cleanup. Automatic legacy workload migration, legacy-ID/URL preservation and backward-compatibility adapters are outside scope. Earlier instructions below to retain legacy execution describe the original M1 landing only and are superseded for M4. The broader replacement-path acceptance cases remain unverified until executed; legacy-compatibility cases are not a cleanup gate.

## Source baseline and scope

The source inventory below records `main` after PR #391. That PR reconciled pre-Node source `57941d99` with restoration candidate `649761f6` and current main; its reviewed head `489a4004d5f79a72f78e5982634a7cedb3fe25e3` merged as `bb12bf68f36b1b271f4ebfe6986add1ad190e125`. It preserved blocked public registration, the Studio registration message, and the GitHub existing-user login/account-creation fix while removing the abandoned Node implementation. There is no dependency on an open restoration PR.

The original M1 acceptance requires one customer-owned management Runner on ordinary Ubuntu to deploy and operate web apps and run finite, isolated Actions for at least two users through the existing control plane. ext4 is a test baseline, not a filesystem restriction. User code, including build and Action code, must run in bounded containers and never in the privileged Runner process. The original M1 landing kept existing Hosted Runner workloads on their current path. The current roadmap removes that legacy code for fresh installations without promising to migrate old workloads. Existing-system deployment and data changes remain separate from isolated development.

The original recommendations below reuse the Runner identity, deployment target, durable operation, package, Action and route mechanisms. Source descriptions record that earlier baseline; they are not claims about current Machine Management behavior.

## Source inventory at the original baseline

### Web deployment path

The CLI packages app source, runtime files and the app contract, then calls the API deploy-package endpoint. The principal client owners are [DeployService](../../src/Automaton.Cli/Services/DeployService.cs) and the package builder in `Automaton.Cli`. In the API, [AppDeploymentController](../../src/Automaton.Api/Controllers/AppDeploymentController.cs) authorizes the app, accepts the package, and exposes the durable operation status. [DeploymentOperationService](../../src/Automaton.Api/Services/DeploymentOperationService.cs) stores the package, creates/claims the operation and attempt, and coordinates completion and retry. [DeploymentOperationDispatcher](../../src/Automaton.Api/Services/DeploymentOperationDispatcher.cs) and its event/worker integration resume pending work; package and attempt identities make duplicate dispatch distinguishable.

The API deployment service has two execution routes. Its durable Hosted Runner command route publishes a deployment command and consumes the Runner's stored result. The generic package route resolves an [AppDeploymentTarget](../../src/Automaton.Infrastructure/Entities/AppDeploymentTarget.cs), selects its assigned Runner through [AppRunnerAssignmentPolicy](../../src/Automaton.Api/Services/AppRunnerAssignmentPolicy.cs), and sends a typed `DeployPackage` transfer through [DeploymentPackageRunnerService](../../src/Automaton.Api/Services/DeploymentPackageRunnerService.cs) and the durable `RunnerExecutionOperationService`. [ApplicationDeploymentService](../../src/Automaton.Api/Services/ApplicationDeploymentService.cs) owns assignment/readiness, target state, package finalization and route reconciliation. The fallback and compatibility branches in `DeploymentOperationService` are significant: do not assume every existing app already follows one uniform Runner path.

On the Runner, [RunnerApplicationDeploymentExecutor](../../src/Automaton.Runner/Services/RunnerApplicationDeploymentExecutor.cs) validates and safely extracts the bounded package, stages source and runtime artifacts, prepares Actions, snapshots/restores previous files on failure, and delegates build and runtime application. A build with a declared image goes through [RunnerApplicationBuildExecutor](../../src/Automaton.Runner/Services/RunnerApplicationBuildExecutor.cs) and Docker; the legacy build executor can run a child process. Runtime selection is in `RunnerApplicationContainerRuntimeSelection`; [RunnerRuntimeContainerManager](../../src/Automaton.Runner/Services/RunnerRuntimeContainerManager.cs) manages container runtimes, while [RunnerRuntimeProcessManager](../../src/Automaton.Runner/Services/RunnerRuntimeProcessManager.cs) retains the process-based compatibility route. Runner results are journaled by `HostedRunnerDeploymentResultJournal` and returned through the durable transfer result path. API target state and route publication are finalized after success.

The current implementation therefore already supplies useful pieces—package contract, stable app/target identities, durable operation attempt IDs, staging, rollback, typed file-transfer results and route refresh—but it still carries Hosted Runner assumptions in command/result journal names and the alternate execution branch. A code name alone does not prove that a new management Runner has the intended assignment, capacity, storage or user authorization semantics.

For Machine Management, the generated self-hosted install command creates a dedicated Docker bridge and passes its inspected gateway address to the Runner. That address is validated as private when the Runner publishes an app container port; `SelfHostedRuntimeTunnelPolicy` and `BackendRouteConfigService` route app HTTP through the existing API tunnel for this profile. The generated path and routing behavior have focused tests, while the end-to-end Linux/ext4 fixture remains a release acceptance requirement.

### Action path and trust boundary

Manual execution enters through [AppActionsController](../../src/Automaton.Api/Controllers/AppActionsController.cs) and [AppActionExecutionService](../../src/Automaton.Api/Services/AppActionExecutionService.cs). The service checks app access and execute permission, resolves the default deployment target and assigned Runner, checks that the Action is deployed there, then persists an `AppModuleExecution` and queues an `execute` command through [AppActionRunnerGateway](../../src/Automaton.Api/Services/AppActionRunnerGateway.cs). Scheduled work starts in [ActionScheduleProcessor](../../src/Automaton.Worker/Services/ActionScheduleProcessor.cs); occurrence identity prevents creating a second execution for the same schedule occurrence. The common API operation record protects the request and binds its ID, actor and Runner. Results are terminal, cancellation is persisted and signaled, and logs/results are fetched through authorized Action artifact commands.

Runner-side Action dispatch is composed in [RunnerHostBuilder](../../src/Automaton.Runner/RunnerHostBuilder.cs), with Action preparation, execution, result persistence and cleanup in `AppActionExecutionService`, `AppActionExecutionCoordinator`, [AppActionExecutionPreparer](../../src/Automaton.Runner/Services/AppActionExecutionPreparer.cs), [AppActionRuntimePreparer](../../src/Automaton.Runner/Services/AppActionRuntimePreparer.cs), `AppActionProcessExecutor` and `AppActionArtifactCleanupService`. Current Action code is launched as a child process in the Runner OS environment by [AppActionProcessExecutor](../../src/Automaton.Runner/Services/AppActionProcessExecutor.cs), with bounded stdout/stderr, timeout/cancellation, secret redaction and schema-checked JSON output. More importantly, web package deployment calls [AppActionDeploymentService](../../src/Automaton.Runner/Services/AppActionDeploymentService.cs), which copies Action files and invokes `AppActionRuntimePreparer`; for Python Actions it creates a virtual environment and runs `pip install -r requirements.txt` on the Runner host. Package installation can execute user-controlled hooks, so isolation is required during deployment as well as invocation. Neither current host process path isolates hostile user code from a management Runner. The existing request contains Action secrets; they must be passed only into the job container, never persisted in plaintext or inherited by the management service or unrelated containers.

Infrastructure and Hosted Runner roles use the same executable but have different capability policy and data ownership. [AppRunnerAuthorizationPolicy](../../src/Automaton.Api/Services/AppRunnerAuthorizationPolicy.cs) applies ordinary Runner visibility/capability checks, but requires an administrator and the trusted infrastructure app for an Infrastructure Runner. [RunnerExecutionAdmissionService](../../src/Automaton.Api/Services/RunnerExecutionAdmissionService.cs) similarly restricts administrator-required capabilities. `TrustedInfrastructureActionExecutor` is the privileged infrastructure Action route. These checks must remain meaningful while management duties consolidate: an ordinary app Action must not become trusted merely because its assigned Runner also manages the machine.

### Container operations and resource ownership

[HostContainerExecutionService](../../src/Automaton.Runner/Services/HostContainerExecutionService.cs) is a typed Docker boundary, not a general Docker argument proxy. It validates operation, scope, image and resource limits, and supports bounded image resolution, build, application-container creation and lifecycle/log operations. It currently requires `AUTOMATON_RUNNER_PURPOSE=Infrastructure` plus the `HostContainerExecution` capability. Its scope requires `HostedRunnerId`, `RunnerHostId`, `AppId` and `DeploymentTargetId`; build and container creation require a trusted Hosted Runner resource mapping. Those are explicit dependencies to replace, not conditions to remove by making arbitrary Docker arguments available to users.

Hosted app placement and capacity in the M1 source baseline were also account/Hosted Runner oriented. [HostedRunnerAppCapacityService](../../src/Automaton.Api/Services/HostedRunnerAppCapacityService.cs) still reads an existing Hosted Runner specification's `MaximumApps` when present and writes the target's `ExecutionRunnerId`. M4 removed the account project-allocation service; the legacy `HostedRunner.StorageProjectId` field remains as a persisted compatibility snapshot and is no longer allocated for new work. Existing Hosted Runner specifications retain CPU, memory, disk, writable-layer, PID, shared-memory, Docker log and app-count fields; `HostContainerExecutionService` applies the currently supported Docker runtime limits. These settings do not establish that every disk byte is hard-limited per user.

[RunnerHostImageStore](../../src/Automaton.Runner/Services/RunnerHostImageStore.cs) currently requires Docker `overlay2` and Docker image/cache storage on a separate XFS filesystem with project quotas. That provisioning contract excludes ordinary ext4. The target must remove this XFS prerequisite for the supported single-machine install. On ext4, host free-space monitoring and admission budgets are observability and scheduling controls, not hard per-user disk quotas. Do not claim a hard disk cap unless a chosen backend actually enforces it. CPU, memory, PID and log bounds can be enforced through supported container settings; storage should use explicit owned paths/volumes, reserved host capacity, usage reporting, cleanup of identified disposable data, and clear admission refusal.

### Readiness, persistent data and routing

`ManagedRunnerBootstrapService` backs the managed-runtime readiness endpoint; it currently reconciles the app's Runner assignment and can report provisioning/availability states. `DeploymentPackageFinalizationService` and `AppDeploymentTargetStateService` update deployment state and reconcile routes. [BackendRouteConfigService](../../src/Automaton.Api/Services/BackendRouteConfigService.cs) writes Traefik's dynamic configuration atomically from active deployment targets, including private and published hostnames, target paths, authentication middleware and runtime tunnel routes. [ManagedRuntimeRouteReconciliationService](../../src/Automaton.Api/Services/ManagedRuntimeRouteReconciliationService.cs) refreshes that configuration at API startup. The Runner runtime managers provide process/container readiness and port information to the existing runtime tunnel. Keep API routing and its authentication boundary; make readiness reflect a healthy workload endpoint before marking deployment ready or switching the route.

Current deployment workspaces and runtime artifact roots are target-scoped in `RunnerWorkspaceService` and `RunnerDeploymentWorkspace`; app persistent-data ownership and migration semantics are not equivalent to disposable source/build/runtime directories. Before introducing a volume path, the implementation must specify who owns it, which machine it is attached to, how backup/restore and app replacement preserve it, and which operations can read it. Do not move or delete an existing app's data as part of source-level assignment changes.

## Target behavior and design choices

Use one stable management Runner identity per customer machine, with an explicit customer/workspace assignment. Keep the current API, Worker, identity service, RabbitMQ/CAP delivery, Runner command/result protocol and app/deployment/action identities. The API remains the authorization authority and durable record owner; the Runner reconciles only assignments and operations it has authenticated permission to manage. Avoid creating a user-visible Hosted Runner record as a placeholder for a machine.

Represent three distinct relationships: customer/workspace ownership of the machine, permission to administer or deploy to that workspace, and placement of an app/deployment target on an eligible machine. Resolve every operation against those relationships on the API and again at the Runner's authenticated assignment boundary. A personal user may own a workspace; a shared project or organization may grant scoped members access. Assignment to a shared machine must not imply access to every app, source tree, secret, execution, log or volume on it. Machine capacity admission is based on the machine's declared/observed budget and current workloads, not a plan that provisions one management Runner per account.

Expose a small typed set of management operations: resolve/pull an approved image, run a bounded build, create/start/inspect/stop/remove an assigned app container, inspect readiness, obtain bounded logs, and remove only app-scoped disposable artifacts. Keep host paths, Docker flags, network names, arbitrary mounts and raw Docker commands out of user payloads. The API authorizes a typed request; the Runner derives host paths, volume names, network scope and limits from its signed/authenticated assignment plus the persisted app contract. Privileged maintenance remains an explicitly administrator-authorized capability, separated from app deployment and job execution.

Deploy with the existing package contract first. For M1, recommend one app container per deployment target with HTTP readiness, bounded resource settings, an explicit persistent data mount and the current app/target route contract. Run declared source builds in a separate build container, copy only declared build output into the app image/artifact, and pull by digest when an OCI image is supplied. Reject unsupported service topology and host-affecting fields; the roadmap's documented Compose subset and multiple related services belong to milestone 2. This uses the existing package and runtime contract and avoids requiring a new service orchestrator to make M1 useful.

Actions are finite job containers with no host socket, host filesystem mount, management credential or shared writable app root. The API supplies only secrets authorized for that Action and execution, and the container receives only those values. Keep existing execution IDs, schedule occurrence IDs, deadline, output schema, bounded logs/results and terminal statuses. Persist the cancellation request, signal the Runner, stop the job container, collect bounded/redacted output, persist one terminal result and remove its temporary container/workspace. If the Runner or response is lost after a job may have caused an external effect, record an indeterminate/lost outcome and require an explicit retry by an authorized user; do not silently execute the same Action again.

Machine storage should have configured roots for images/cache, disposable build and job data, app runtime artifacts, and explicit persistent app data. Report per-category usage and machine free space. Use admission budgets and a host reserve to refuse work before it threatens machine/control-plane availability. Keep CPU/memory/PID/log limits as container-enforced where available. On ext4, mark app disk figures as observed/admission estimates, not hard per-user limits. Remove the mandatory XFS quota dependency and avoid claiming an account-level quota based on the existing allocation records.

The user-visible flow must be complete across API, Studio and CLI: enroll/identify a machine; attach a workspace; assign an app target; show Runner health and placement; deploy and observe readiness/routes/logs; operate persistent data without accidentally deleting it; run/cancel an Action and view status/result/logs. API routes must enforce deploy, execute, files, logs, secrets and cancellation permissions regardless of UI state. Update Administrator docs alongside any administrator-visible settings or operational steps.

## Recommended implementation PR sequence

Keep the PRs ordered and independently reviewable. Each preserves existing Hosted Runner execution for workloads not yet assigned to the new machine path. The first PR can include schema and API policy in one change because those changes do not deliver value without a coherent assignment boundary; avoid a standalone framework or abstract “machine orchestration” layer.

### PR 1 — Machine/workspace assignment and safe typed management boundary

**Depends on:** PR #391 baseline; existing Runner enrollment/authentication and current project/organization membership model.

**Owners and likely files:** API entities/context/migrations under `src/Automaton.Infrastructure/Entities/` and `Data/ApplicationDbContext*`; Runner identity/enrollment in `src/Automaton.Api/Services/RunnerExecutionIdentityService.cs`, `src/Automaton.Api/Services/AppRunnerAuthorizationPolicy.cs`, `src/Automaton.Api/Services/AppRunnerAssignmentPolicy.cs`, and corresponding Runner API-key/assignment handlers; typed host boundary in `src/Automaton.Core/Models/HostContainerExecution*` and `src/Automaton.Runner/Services/HostContainerExecutionService*`; assignment and storage code near `HostedRunnerAppCapacityService` and workspace storage admission. The account XFS project allocator described in the M1 baseline was removed during M4 cleanup. API/Runner tests live in `src/UnitTests/Automaton.Api.Tests` and `src/UnitTests/Automaton.Runner.Tests`.

**Required behavior:** add the minimum persisted machine/workspace assignment needed to bind a management Runner to customer-owned workspaces and app targets. Enforce workspace membership/role at API admission, bind Runner operations to current machine assignment and app target, reject revoked/stale ownership, and make assignment/capacity writes concurrency-safe. Replace Hosted Runner-only scope fields in the typed container contract with machine/workspace/app/target identity and server-derived resource mapping. Keep Infrastructure-only operations administrator-only; ordinary deploy/build/job operations receive narrowly scoped typed authorization and never arbitrary Docker/host access. Add an ext4-compatible storage-root contract and accurate capacity fields; retain compatibility for old Hosted Runner records and their path.

**Acceptance evidence:** API tests prove owner/member/outsider outcomes for assignment and each typed operation, including revocation and duplicate assignment races. Runner tests prove incomplete, stale, cross-machine and cross-app scopes fail closed; allowed operations generate only policy-built Docker arguments. An ordinary user payload cannot select a host path, Docker option, privileged mode, socket, network or secret source. A Linux ext4 fixture passes storage admission while current legacy Hosted Runner fixtures retain their documented behavior. No user-controlled app or Action is yet executed in the management process.

**Decision before code:** select the persisted machine identity. Recommendation: bind the new machine assignment to the existing authenticated Runner identity and reuse `RunnerHost` only as an optional enrollment/host inventory record where it already provides durable provisioning metadata; do not require `HostedRunner` for the management Runner. Add a distinct machine entity only if a Runner can manage multiple independently owned machines or the current Runner identity cannot represent one machine without ambiguity. The current source does not prove that a `RunnerHost` is already the canonical customer-machine identity, so this schema choice needs a short model review before migration code.

### PR 2 — Complete web deployment on one assigned management Runner

**Depends on:** PR 1 assignment and typed operation contract.

**Owners and likely files:** `AppDeploymentController`, `DeploymentOperationService`, `DeploymentOperationAdmission`, `DeploymentOperationDispatcher`, `ApplicationDeploymentService`, `DeploymentPackageRunnerService`, `DeploymentPackageFinalizationService`, `ManagedRunnerBootstrapService`, `BackendRouteConfigService`; Runner `RunnerApplicationDeploymentExecutor`, `RunnerApplicationBuildExecutor`, `RunnerApplicationContainerRuntimeSelection`, `RunnerRuntimeContainerManager`, `RunnerWorkspaceService`, and `RunnerHostImageStore`; CLI `DeployService` and package contract; deployment, route, build and runtime tests in the API/Runner/CLI test projects. Studio placement/readiness surfaces are updated if their current behavior assumes per-user Hosted Runner provisioning.

**Required behavior:** new machine-assigned targets use the existing durable package operation and attempt IDs end to end: upload, isolated build or image pull, candidate creation/start, bounded health/readiness, route activation, logs/result, stop/update and cleanup. This path also handles Action files as untrusted package contents: either prepare dependencies inside a bounded container with no management-host access, or explicitly reject/defer Action dependency preparation until that isolated preparation is available in PR 3. The recommended safe landing is to reject/defer preparation in PR 2 if containerized dependency setup is not ready; never run `pip install` or equivalent package hooks on the management host. Use target-scoped runtime state and an explicit persistent data root that survives redeploy/restart; preserve it when replacing app code. Route changes occur only after readiness and failed replacement leaves the previous healthy route/runtime intact where rollback is possible. Store packages/results so API/Worker replicas can recover them, or explicitly reject unsupported cross-replica operation in the deployment topology. Remove Hosted Runner provisioning and Hosted Runner command/result dependencies from this new path without deleting old-workload support. Do not claim ext4 disk quota enforcement.

**Acceptance evidence:** Linux Docker tests deploy from the existing CLI package contract and an OCI digest on ext4; wait for readiness; verify target/public/authenticated routes, bounded logs, stop/update, failed-update rollback, persistent data across app update and Runner restart, capacity refusal and cleanup. Include an Action package with a dependency-install hook that would create a host-visible marker or contact a test endpoint: deployment must prove that the hook cannot execute on the management host. If Action preparation is deferred, prove that deployment rejects/defers it before invoking the installer and reports a clear supported-state result. API/Worker duplicate delivery and lost response return the persisted operation result without launching a second deployment attempt with conflicting ownership. Legacy unassigned/Hosted Runner targets still complete through their existing route. Two workspaces on one machine cannot inspect each other's files, logs, artifacts, secrets or containers.

**Decision before code:** define the M1 package/build input and readiness contract in the app manifest/API. Recommendation: preserve the existing source-package manifest and declared `Build`/`Runtime` contract, run any build command only in an isolated bounded container, accept digest-pinned OCI images, and require an HTTP health check for a routed service (with a bounded startup timeout). Do not add Compose in this PR; reject unsupported multi-service/host settings explicitly. This is the smallest useful slice compatible with the current CLI package builder and runtime target model.

### PR 3 — Isolated Action jobs and complete Studio/API/CLI flow

**Depends on:** PR 1 authorization and typed operation boundary; PR 2 machine assignment and storage/operation handling may proceed in parallel only if both changes agree on the stable machine/workspace/target contract. Merge PR 2 first for the recommended sequence so Action jobs share its capacity and cleanup rules.

**Owners and likely files:** API `AppActionsController`, `AppActionExecutionService`, `AppActionRunnerGateway`, `RunnerExecutionOperationService`, `RunnerExecutionAdmissionService`, `ActionScheduleProcessor` and schedule Worker dispatch; Runner `AppActionExecutionService`, `AppActionExecutionCoordinator`, `AppActionExecutionPreparer`, `AppActionRuntimePreparer`, `AppActionDeploymentService`, `AppActionProcessExecutor`, `AppActionArtifactCleanupService`, `HostContainerExecutionService` and typed job operation; Studio API clients/views and CLI Action commands; `src/Automaton.Api/Documentation/Admin/` where machine assignment or limits are visible. Tests in API, Worker, Runner, Studio type-check and CLI projects.

**Required behavior:** execute Action code only in a finite job container. If PR 2 deferred Action dependency setup, add it here in a bounded preparation container before reporting the Action as deployable; `AppActionRuntimePreparer` must not return to host-side package installation. Scope input, approved secrets, app artifact access, temporary storage, output/result and logs to the authorized workspace/app/target/execution. Preserve schema validation, deadlines, cancellation and schedule occurrence identity. Persist one terminal result and never automatically replay an uncertain Action. Cancellation must terminate the exact execution container, including after an API/Worker restart. Cleanup removes the job and preparation containers and their temporary files without touching app persistent data. Update Studio and CLI to create, monitor, cancel and inspect Actions against the shared management Runner, while API checks remain authoritative.

**Acceptance evidence:** two users run concurrent scheduled and manual jobs on the same Runner and receive isolated outputs; authorization tests deny cross-user source/file/secret/log/result access, cancellation of another user's execution, and arbitrary execution/host control. Tests cover container timeout, user cancellation, Runner loss before and after side effect, duplicate schedule delivery, duplicate API command, lost result response, restart recovery, output limits, secret redaction and cleanup. UI/API type checks and relevant CLI tests show the same execution identity and final status end to end.

**Decision before code:** define the terminal status for an operation whose side effect may have happened but whose result is unavailable. Recommendation: retain the existing `Lost`/interrupted terminal outcome, surface it as “outcome unknown; retry manually,” and never auto-requeue the same execution ID. Add a new persisted state only if the existing client contract cannot distinguish that result from a known failure; this should be decided before changing status enums or schema.

The three PRs are a recommended review order, not three mandatory gates for every helper. If implementation discovers that PR 1's schema can safely remain additive and PR 2 can carry its first consumer in the same review, combine them; do not split type/helper changes with no independent behavior. Do not migrate existing Hosted Runner workloads in these PRs.

## Focused verification for milestone 1

Build fixtures around actual boundaries and failure modes rather than duplicating helper logic. Use two distinct users/workspaces and one machine Runner, with a Linux Docker/ext4 integration fixture for behavior the in-memory API/Runner tests cannot establish.

- **Shared machine:** both users can deploy an authorized app and execute an authorized Action through the same machine identity; capacity admission is deterministic under concurrent assignments and refuses work without creating orphan containers or target state.
- **Authorization:** unauthorized users cannot enumerate/read app files, source, artifacts, environment secrets, Action secrets, logs or results; cannot exec, stop, cancel, delete or inspect another workspace's container/operation. Test revoked membership, Runner credential revocation, stale assignment and cross-app/target IDs at both API and Runner boundaries.
- **Execution isolation:** attempt to read host and sibling workspace paths, environment, Docker socket and management credentials from build/app/Action containers; all must be unavailable. Verify only explicitly scoped secrets reach the relevant Action, outputs redact them, and size/time/resource limits are enforced where the platform supports them.
- **Deployment and routing:** readiness must precede route activation; test healthy start, timeout/unhealthy start, update failure rollback, private/public/authenticated route selection, stop, logs, target separation and route refresh after API restart. Verify persistent app data survives source/runtime replacement and Runner restart, while disposable build/job data is removed.
- **Storage claims:** ext4 is a supported fixture. Assert host reserve/admission and monitoring behavior separately from Docker CPU/memory/PID/log enforcement. A test must not imply ext4 provides a hard per-user disk quota. Confirm cleanup never removes an owned persistent path.
- **Durable operation behavior:** duplicate API/Worker delivery, duplicate Runner poll, lost API response after effect, Runner restart before/after execution, expired leases, cancellation race and unavailable artifact/result storage. Deployment may resume through stable attempt ownership; an Action with uncertain effects is reported lost/unknown and not rerun automatically.
- **Historical legacy compatibility:** the original M1 landing retained Hosted Runner fixtures while adding the new path. That compatibility requirement is superseded for M4 fresh-install cleanup; do not retain old execution consumers or build migration adapters to satisfy it.

For later C# implementation PRs, follow the repository-required pre-edit affected-project nonincremental build and analyzer review, affected-project build/tests after editing, and final `dotnet build Automaton.All.sln -c Debug --no-incremental -v minimal`. Run focused API/Worker/Runner/CLI tests and Studio `npm run type-check && npm run build` when those sources change. Add Linux/container and database fixtures only where they establish the behavior above; do not run broad unrelated suites repeatedly. This guide-only change requires link validation and `git diff --check`, not builds or runtime tests.

## Completion, later work and release boundary

Milestone 1 is complete when the end-to-end shared-machine acceptance above passes: machine/workspace/app assignment is authorized and durable; web deployment reaches a healthy routed workload with preserved explicit data; finite Actions execute in isolated containers with results, logs, cancellation, limits and cleanup; two users remain isolated; ext4 is supported with accurately stated disk guarantees; and restart, duplicate delivery and uncertain outcomes behave safely. Updating a UI to show machine fields or adding typed operation scaffolding alone is not completion.

M2 implementation, including the supported Compose subset, shared static publishing, organization app use and basic capacity safeguards, is merged. The current roadmap narrows M3 to the single-server install/CLI deployment demonstration, then prioritizes M4 legacy removal for fresh installations without automatic migration. Second-machine acceptance and optional operations/features remain deferred until after cleanup. Any existing-installation retirement, export/manual redeployment, database reuse/reset or production deployment remains a separate operator decision. These are not prerequisites for implementing fresh-install cleanup.

Do not add Node, a new transport or operation store, VM provisioning, a custom orchestrator, an implied promise of ext4 per-user disk quotas, or shared abstractions without a current consumer. Keep the existing control plane and durable Runner operation mechanisms, and keep user code outside the trusted management process.
